## Acceptance Criteria

### AC1 — Inspect the source basis behind recommendation logic and outputs

**Given** recommendation outputs have been generated by the system
**When** I review internal recommendation trust surfaces
**Then** I can inspect the source basis behind recommendation logic and outputs
**And** I can assess whether recommendation claims remain aligned with current policy conditions

### AC2 — Mark, pause, or trigger corrective action for stale/weak/questionable support

**Given** a recommendation or source is stale, weak, or questionable
**When** I identify the issue in the admin workflow
**Then** I can mark, pause, or otherwise trigger corrective action for the affected trust input
**And** the workflow supports preventing continued reliance on weak support

### AC3 — Citation integrity and internal review linkage

**Given** I validate recommendation claims internally
**When** I inspect trust details
**Then** I can confirm whether the claims remain properly cited and reviewable
**And** the internal review flow preserves enough linkage to support trust decisions without exposing user-private data unnecessarily

## Dev Notes

### Context & Purpose

This is the **third story in Epic 5**. It adds the recommendation trust review capability for internal admin/ops users. The previous stories (5.1, 5.2) delivered the pathway inventory, pathway rules editor, and evidence sources curation. This story enables admins to **inspect** the recommendation outputs themselves, validate that citations are intact and current, and take corrective action when trust issues are detected.

The story creates a new admin page at `/admin/recommendation-reviews` using the **Citation Integrity Inspector** layout (Concept B), which uses a two-panel master-detail pattern: a run list on the left and a deep citation-level inspector on the right.

### What Already Exists (Developer Guardrails)

> [!IMPORTANT]
> This is a brownfield implementation. The following infrastructure is already in place and MUST be reused.

**Admin Infrastructure (from Stories 5.1 and 5.2):**
- `app/middleware/admin.ts` — Route middleware that checks `/api/admin/access`, redirects unauthenticated users to `/auth` and unauthorized users to `/workspace`
- `server/utils/auth/requireAdminSession.ts` — Server-side admin session guard used by all existing admin API routes
- Existing admin pages at `app/pages/admin/` — `pathways.client.vue`, `pathway-rules.client.vue`, `evidence-sources.client.vue`, `rag-sources.client.vue`, `rag-phase0.client.vue`
- Existing admin page shell pattern: left sidebar navigation from `app/lib/admin/navigation.ts`
- `app/components/admin/PathwayStatusBadge.vue` — Reusable status badge pattern

**Recommendation Run Infrastructure (from Epics 2–4):**
- `convex/recommendationRuns.ts` — Convex module with full recommendation run data model including: lifecycle statuses (`queued`, `evaluating`, `completed`, `degraded`, `failed`), ranked recommendations (`RankedDirectRecommendation`, `RankedBlockedRecommendation`, `RankedComposedRecommendation`), and rich metadata including `confidence`, `freshness`, `caveat`, `fitSignals`, `blockers`, `tradeoffs`, `improvementActions`
- `app/composables/useWorkspaceRecommendationReview.ts` — User-facing composable for loading recommendation runs and results (NOTE: this is user-scoped, admin endpoints will need their own cross-user query pattern)
- `app/lib/recommendation-lifecycle.ts` — Canonical status utilities: `isCanonicalRecommendationStatus()`, `isInProgressStatus()`, `getDefaultStatusMessage()`

**Evidence Sources Infrastructure (from Story 5.2):**

- `server/utils/evidence/evidenceSourceService.ts` — CRUD service: `listEvidenceSources()`, `updateEvidenceSourceStatus()`
- `server/api/admin/evidence-sources/` — Admin API endpoints for evidence source management including status updates (pause/resume)

**Pathway Definitions Infrastructure (from Story 5.1):**
- `server/db/schema/pathwayDefinitions.ts` — Drizzle schema for `pathway_definitions` table
- `server/utils/pathways/pathwayDefinitionService.ts` — CRUD service for pathway definitions

### Architecture Constraints

1. **Server-mediated security boundary:** All admin API routes MUST use `requireAdminSession` guard. No direct Convex or DB access from the browser.
2. **Split persistence model:** Recommendation runs and results are in **Convex**; pathway definitions, evidence sources, and review state are in **PostgreSQL** via Drizzle. The review service must aggregate across both stores.
3. **Data privacy:** The admin review page shows recommendation run metadata and citation basis but MUST NOT expose user-private profile data. Anonymize user references (e.g., use anonymized IDs or initials, not full profiles).
4. **Brownfield convention:** Follow the existing admin page patterns exactly — `.client.vue` suffix, sidebar navigation from `navigation.ts`, same component folder structure.
5. **Audit deferred:** Full audit logging of corrective actions is owned by Story 5.4. This story should track review state changes but does not need to implement the persistent audit log.

### Key Data Flow

```mermaid
flowchart LR
    A[Admin Browser] -->|$fetch| B[/api/admin/recommendation-reviews/*]
    B -->|requireAdminSession| C[recommendationReviewService]
    C -->|Query runs + results| D[(Convex)]
    C -->|Query evidence sources + pathway defs| E[(PostgreSQL)]
    C -->|Build review projection| F[Admin Review Response]
    F --> A
    A -->|Corrective action| G[/api/admin/recommendation-reviews/.../flag,resolve,dismiss]
    G -->|Update review state| E
    G -->|Optionally pause source| H[evidenceSourceService]
```
