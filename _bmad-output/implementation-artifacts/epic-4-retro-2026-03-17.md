## Story-Level Signals (What We Learned)

## Story 4.1

- Strong foundation: next-step planning was added by extending the existing recommendation explanation pipeline rather than introducing a competing planning model.
- Key learning: next-step guidance must stay server-owned and trust-aware so blocked or low-confidence recommendations do not read as stronger than they are.
- Pattern: recommendation-specific action plans work best when they stay adjacent to blockers, tradeoffs, and trust metadata inside the same review surface.

## Story 4.2

- Strong foundation: preserved run history created a durable continuity layer instead of treating recommendation runs as disposable session output.
- Key learning: archived playback, unavailable states, and history filtering need explicit handling or the continuity experience becomes misleading.
- Pattern: shared result readers and normalized archive payloads make later features easier to build without duplicating logic.

## Story 4.3

- Strong foundation: comparison became a server-owned diff model grounded in preserved recommendation runs and profile snapshots.
- Key learning: trust and evidence differences must remain visible in comparisons instead of being flattened into generic status changes.
- Pattern: history, compare, and review flows need context-preserving navigation or the workspace starts to feel fragmented.

## Story 4.4

- Strong foundation: the workspace landing page now behaves like a continuity hub instead of a first-run welcome screen.
- Key learning: new-cycle and refresh flows require careful lineage handling or preserved history and comparison integrity can drift.
- Pattern: summary/read-model APIs keep the dashboard thin and reduce the temptation to infer workflow state in the client.

## Cross-Story Patterns

### What Went Well

1. The epic delivered a coherent user-value progression: act on a recommendation, revisit prior runs, compare changes, then return to a persistent planning workspace.
2. Preserved run data and normalized server contracts were reused across the epic instead of spawning disconnected feature-specific models.
3. Quality practices improved as the epic progressed. API, component, and E2E verification became routine.
4. User-facing complexity stayed mostly behind the curtain. The Project Lead reported the epic simply "went well," which signals good product-level coherence.
5. The workspace now feels like an ongoing planning tool rather than a one-time recommendation result screen.

### What Was Painful

1. Continuity behavior across history, compare, archived review, and live review required repeated tightening.
2. Preserved-state and source-run lineage logic was more delicate than it first appeared.
3. Duplicated recommendation and trust-sensitive types remain architectural debt and create maintenance pressure.
4. Operational closure evidence is still weak. Stakeholder acceptance and release-state recording are not consistently captured in durable artifacts.

### Recurring Review Themes

- Keep recommendation and trust-sensitive behavior server-owned.
- Preserve honest unavailable, degraded, failed, and fallback states.
- Normalize data before it reaches the UI instead of compensating in components.
- Preserve navigation context across history, compare, and review flows.
- Tighten lineage handling so new-cycle and refresh flows do not damage preserved continuity.

### Breakthroughs

1. Story 4.2 established preserved run history as the continuity backbone for the rest of the epic.
2. Story 4.3 turned that preserved history into meaningful decision support through trustworthy run-to-run comparison.
3. Story 4.4 unified the prior work into a planning workspace that supports repeated use over time.
