## Story-Level Signals (What We Learned)

## Story 3.1

- Strong foundation: recommendation rationale and fit signals became explicit domain data instead of display-only decoration.
- Key learning: missing profile context must fail safely or downgrade honestly rather than being guessed in the client.
- Pattern: trust cues work best when tier meaning, caveats, and fit semantics are rendered as visible text and stable hooks.

## Story 3.2

- Strong foundation: blockers, tradeoffs, and next actions became separate normalized modules rather than one blended explanation blob.
- Key learning: strong-fit recommendations must not fabricate blocker or action content when conditions are already satisfied.
- Pattern: semantic separation in the contract makes the UI clearer and makes review findings easier to localize.

## Story 3.3

- Strong foundation: comparison metadata and pathway type became first-class server-owned fields that support both side-by-side comparison and truthful fallback states.
- Key learning: comparison logic is trust-sensitive and should not be inferred in Vue templates or browser test factories.
- Pattern: comparison views need explicit failed-run and zero-result behavior, not just happy-path multi-candidate layouts.

## Story 3.4

- Strong foundation: citations and trust boundaries now travel with recommendation results and can be inspected in the same workspace surface.
- Key learning: accessibility issues around disclosure, keyboard reachability, and duplicated labels surface quickly when citation UX is added late.
- Pattern: provenance must be honest; synthesizing citations, timestamps, or trust labels in the API layer undermines the product's core trust promise.

## Cross-Story Patterns

### What Went Well

1. The epic built in the right order: explanation -> blocker/tradeoff clarity -> comparison -> trust/citation depth.
2. Server-owned truth remained the dominant architecture pattern and prevented frontend convenience shortcuts from hardening into product behavior.
3. Review cycles materially improved quality. The team caught fabricated or inferred trust semantics before they became user-facing debt.
4. The recommendation workspace matured into a coherent decision surface rather than a flat result dump.
5. Accessibility and automation hooks became part of the acceptance bar instead of an afterthought by the end of the epic.

### What Was Painful

1. Contract drift between server and client appeared multiple times and required repeated review correction.
2. Story/state artifact synchronization drifted. Story 3.3 still describes pending validation conditions even though sprint tracking marks it done.
3. Accessibility details around mobile disclosure, keyboard order, and citation inspection were discovered later than ideal.
4. Test fixture duplication and mirrored types across server, client, and tests created unnecessary maintenance pressure.
5. Release-state and stakeholder-acceptance evidence remain weak in the implementation artifacts even when technical completion is strong.

### Recurring Review Themes

- Remove client-side inference from trust-sensitive UI paths.
- Keep server and browser contracts aligned, especially for required arrays and metadata fields.
- Preserve honest fallback behavior for failed, degraded, and zero-result states.
- Tighten accessibility behavior for disclosure controls, links, labels, and touch targets.
- Keep story artifacts and sprint tracking synchronized after review and validation changes.

### Breakthroughs

1. Story 3.1 established explanation and fit semantics as durable recommendation data rather than ad hoc copy.
2. Story 3.3 converted comparison logic into a trustworthy server-owned model that Epic 4 can now build on.
3. Story 3.4 completed the trust loop by linking recommendation claims to inspectable citation context on the same surface.
