# Recommendation engine and production-readiness review

Review date: **2026-11-16**. Repository: **cadet2**. Reviewed commit: **`67b5ea364678a363630acba248e467489efef315`**, branch `t3/project-feasibility-deep-dive`. Initial working tree was clean. The latest commit is dated 2026-03-26; this is a review of that source snapshot against present-day operating requirements, not proof of what is deployed.

## Decision

**Do not launch this checkout as a trustworthy, personalized immigration recommendation service.** It has useful intake, history, presentation, source-management, and governance scaffolding. Its decision engine implements three generic planning categories with eight simple predicates. It does not model the actual federal/provincial program system with sufficient fidelity. Its strongest immediate security defect is that public Convex functions expose recommendation data and mutations without authenticating the caller.

The practical path is to retain the application shell, make the data boundaries safe, and replace the catalog with a small, professionally reviewed, effective-dated rules engine. Limit launch coverage explicitly. Keep deterministic evaluation authoritative; make language models optional assistants for structured extraction, explanation, and evidence-grounded questions.

### Evidence and limits

- **Verified from code:** definitions, call chains, schemas, route guards, configuration, test contents, and the specific branches cited below. A branch's consequences can be established statically without invoking a deployed backend.
- **Inference:** operational impact, likely attack scenarios, engineering estimates, and architecture recommendations. Scenarios below are derived from code and should be tested in an isolated environment; they were not executed against a service.
- **Externally verified:** primary government/provider documentation accessed on 2026-11-16, linked beside relevant claims. Mutable pages are observations, not retained source snapshots. Exact legal applicability and service contracts still need professional/owner review.
- **Unrun / unverified:** builds, typecheck, automated tests, browser flows, dependency audit, live provider API calls, production database contents, deployed Convex exports, CI results, hosting region, provider account settings, penetration tests, backups, and recovery drills. No packages were installed and no servers were started. The sole created file is this report.
- File references are relative to the repository root; line numbers refer to the pinned commit. Absence findings mean no implementation was found in the reviewed runtime/configuration surface, not that an external platform control cannot exist.

## 1. What the engine actually does

### End-to-end standard run

1. **Collect and save a structured intake draft.** `POST /api/intake/draft` obtains the Better Auth user, parses the draft schema, normalizes values, and upserts one PostgreSQL `intake_draft` row per user (`server/api/intake/draft.post.ts:37-82`). This is not LLM extraction. The intake contains personal, education, work, immigration, and goals sections.
2. **Submit a profile snapshot and create a queued run.** `POST /api/intake/submit` loads that user's draft, requires section-complete flags and nonempty required values, creates random snapshot/run identifiers, inserts the submitted JSON into PostgreSQL, then calls Convex `createQueuedRun` (`server/api/intake/submit.post.ts:132-151,154-190,213-256`). A caught Convex error triggers a compensating SQL deletion (`:258-269`). These are two separate persistence systems, without one transaction or durable outbox.
3. **The client/request must start processing.** `POST /api/recommendations/runs/:runId/start` obtains the user from the session, reads the owned run, transitions it through Convex, and then awaits eligibility, ranking, and finalization inside the HTTP handler (`server/api/recommendations/runs/[runId]/start.post.ts:92-119,130-145,250-259,272-325`). This is synchronous orchestration around stored lifecycle states, not a durable background evaluation worker.
4. **Load the submitted input and current active rules.** The evaluator reads the PostgreSQL profile by both `snapshotId` and `userId`, resolves the pathway catalog, then writes direct/blocked outcomes to Convex (`server/utils/recommendations/evaluatePathwayEligibility.ts:49-68,71-104`). Inventory and rules actually live in PostgreSQL, not Convex.
5. **Normalize to only eight decision inputs.** `englishClb`, skilled-experience years, funds, valid-job-offer yes/no, relocation yes/no, study intent yes/no, budget, and timeline are the entire normalized eligibility profile (`server/utils/pathways/mvpPathwayCatalog.ts:9-18`; `evaluateDirectAndBlockedPathways.ts:79-93`). Invalid/missing numbers become zero; malformed/missing yes/no strings become false (`evaluateDirectAndBlockedPathways.ts:56-76`). There is no explicit unknown result.
6. **Evaluate an AND of predicates.** Every rule must pass for a pathway to be `direct`; otherwise its unmet-condition IDs become `blocked` (`evaluateDirectAndBlockedPathways.ts:100-129`). This is deterministic code, optionally populated from a flat stored DSL. No LLM judgment is used here.
7. **Create at most one composed suggestion.** An already-direct pathway becomes a bridge to one blocked target, with a hardcoded improvement string. There must be a direct anchor; the generator stops after the first composition (`server/utils/pathways/generateComposedPathways.ts:30-83,86-128`). It does not simulate future eligibility or traverse a real immigration-state graph.
8. **Rank with fixed arithmetic.** Candidates are alphabetically ordered within type. Direct scores are `90 - 3*index`; blocked scores `58 - 6*unmetCount - 2*index`; composed scores `74 - 3*max(0,steps-1) - 2*index` (`server/utils/recommendations/rankRecommendationCandidates.ts:84-105,176-212`). These scores are neither CRS nor probabilities. Preferences such as fastest/cheapest/highest odds do not enter the ranker's input contract (`:59-69`).
9. **Attach heuristic trust labels and templates.** Scores/tier produce qualification, confidence, and freshness (`qualifyWeakRecommendationResults.ts:63-126`), then TypeScript templates add rationale, fit signals, blockers, tradeoffs, and actions (`generateRankedRecommendations.ts:181-262`; `buildRecommendationRationale.ts:95-139,298-327`). The engine's rationale is not generated by an LLM.
10. **Persist and display.** Ranked results are written to Convex, followed by a separate terminal-status mutation (`generateRankedRecommendations.ts:265-282`; start handler `:317-325`). Results reads normalize candidates, derive trust boundaries, and build next-step plans and comparison summaries (`readRecommendationResultsForUser.ts:304-345,450-493`). History and comparisons join Convex run state to owned PostgreSQL snapshots (`server/api/workspace/runs/[runId].get.ts:32-83`; `runs/compare.get.ts:66-85,127-163`).

**Engine classification:** deterministic rules plus heuristic ranking and template explanations. The separately implemented RAG/search playground supports retrieval and provider-generated answers, but it is not connected to the standard recommendation chain. Gateway/OpenRouter fields are configuration/readiness scaffolding (`nuxt.config.ts:21-31`; `server/utils/rag-foundation.ts:128-170`); no OpenRouter generation call was found in the reviewed runtime. The RAG architecture explicitly describes its answer-composition layer as planned/draft (`docs/rag-v1-architecture.md:1-27,125-135`). Do not cost or market the current recommendation run as an LLM/RAG-based assessment.

### Actual coverage and fidelity

There are **three executable pathway IDs**, not three fully modeled immigration programs and not a comprehensive Canadian inventory. Admins can create other inventory rows, but execution filters active IDs to `MVP_PATHWAY_IDS` (`pathwayDefinitionService.ts:295-299`). The actual live database row count is unknown.

| Executable category | Seeded predicates | What the result really establishes |
| --- | --- | --- |
| `mvp-skilled-worker` | English CLB ≥8; skilled experience ≥2 years; funds ≥CAD 15,000 | Three supplied values cross demo thresholds; no FSW/CEC/FST eligibility or invitation eligibility is established. |
| `mvp-provincial-nominee` | Valid job offer = yes; relocation = yes | Two boolean values pass; no province, stream, employer, occupation, nomination, or intake availability is checked. |
| `mvp-study-to-work` | Study/retraining intent = yes; budget ≥CAD 25,000; timeline ≥10 months | Planning preferences pass; no study-permit, DLI, PGWP, or subsequent PR entitlement is established. |

Evidence: `server/utils/pathways/mvpPathwayCatalog.ts:1-5,36-102`. These are the source defaults; admin edits may change thresholds at runtime.

| Domain requested for review | Verified implementation | Production implication |
| --- | --- | --- |
| CRS / Express Entry selection | No CRS calculator, factor breakdown, FSW 67-point grid, CEC/FST program distinction, category/draw model, or tie-break processing in the evaluator/DSL. | A score of 90 is an internal ordering score. It must never be presented as CRS or approval odds. |
| NOC / TEER | Intake requires `nocTeerCategory`; evaluator ignores it (`submit.post.ts:60-66`; normalized profile above). | TEER, duties, occupation version, paid work, hours, continuity, overlap, and lookback windows are unverified. |
| Language | One supplied aggregate `englishClb`; no four-skill IELTS/CELPIP/PTE/TEF/TCF conversion, NCLC/French, approved-test/date validity. | Passing a scalar cannot prove all required language abilities or identify the correct program threshold. |
| ECA / education / age / spouse | Intake asks DOB, education, ECA status, marital status and dependants (`submit.post.ts:43-59`); none appears in the eight-field evaluator. | Unrecognized foreign education, age points, spouse factors, and family size do not affect eligibility/ranking. |
| Funds | One flat CAD 15,000 default threshold. | Family-size amounts, exclusions/exemptions, availability of funds, and application/decision dates are absent. |
| Provincial nomination | A single generic offer/relocation category. | No province-specific streams, nomination process, EOI scores, employer eligibility, closure/cap/draw state, or federal/provincial stage separation. |
| Quebec | Intended province is collected (`submit.post.ts:68-75`), ignored by evaluator. | No Quebec selection/CAQ/CSQ process or federal outside-Quebec restriction is enforced. |
| Study / PGWP | Three planning thresholds only. | No DLI/program eligibility, credential/CIP field, application-date cohorts, study mode, maintained full-time status, deadline, language, prior PGWP, passport limit, PAL/TAL exemptions or annual cap rules. |
| Other domains | Intake goals include family sponsorship and business (`intakeSchemas.ts:11-17`) but executable IDs remain the same three. | Unsupported goals must trigger coverage abstention; users cannot infer that omitted routes are unavailable. |

For a concrete external comparison, IRCC's FSW page requires qualifying TEER 0–3 experience, at least one continuous year/1,560 hours, language minimums in all four abilities, education/ECA, and a separate 67-point selection assessment. The code's CLB-8/two-year shortcut can wrongly reject qualifying profiles and accept nonqualifying profiles. This is a **code/policy mismatch**, not a complete legal assessment of any individual. [IRCC FSW requirements](https://www.canada.ca/en/immigration-refugees-citizenship/services/immigrate-canada/express-entry/who-can-apply/federal-skilled-workers.html).

IRCC's funds page uses family size and exemptions, rather than one amount; its displayed table is explicitly date-stamped. Store the observed table and effective period instead of copying an amount from this review. [IRCC proof of funds](https://www.canada.ca/en/immigration-refugees-citizenship/services/immigrate-canada/express-entry/documents/proof-funds.html).

PGWP eligibility depends on institution/program, study history, deadlines, language, and sometimes field of study and application cohort. PAL/TAL rules also have dated exemptions and validity periods. These cannot be represented by budget and study intent. [IRCC PGWP eligibility](https://www.canada.ca/en/immigration-refugees-citizenship/services/study-canada/work/after-graduation/eligibility.html), [PAL/TAL requirements](https://www.canada.ca/en/immigration-refugees-citizenship/services/study-canada/study-permit/get-documents/provincial-attestation-letter.html).

### Rules representation, mutation, and replay

- The DSL allows **eight fields and six comparison operators**, with scalar number/boolean/string comparison values; there are no nested AND/OR/NOT expressions, exceptions, date cohorts, evidence dependencies, or program/draw entities (`server/utils/pathways/pathwayRuleSchema.ts:3-37,78-99`). All rules on a pathway are implicitly conjunctive.
- Stored rules have IDs, condition IDs, field/operator/value, display order, creation and update times. They have **no immutable revision ID, effective-from/to dates, authority references, approval state, or rule-set digest** (`server/db/schema/pathwayRules.ts:12-29`). An update timestamp is not a reproducible policy version.
- Reads perform schema creation/seeding (`pathwayDefinitionService.ts:105-145`; `pathwayRuleService.ts:232-260`). Deleting every stored rule for a seeded pathway causes the next ensure/read to seed its defaults again. Missing-relation handling can restore the full in-code catalog, even when the current configured inventory should be authoritative (`pathwayDefinitionService.ts:300-324`). Production should fail closed on missing approved policy.
- Bulk replacement deletes the rules and inserts their replacements in separate awaited SQL calls with no transaction (`pathwayRuleService.ts:501-544`). A duplicate condition ID can pass array parsing, hit the database uniqueness constraint, and leave the prior rules deleted. Concurrent reads can also seed defaults between delete and insert. The outcome is inferred from the statements and constraint, not a run test.
- Convex writes store constant strings `mvp-pathway-catalog-v1` and `mvp-recommendation-ranking-v1` (`convex/recommendationRuns.ts:1065-1071,1140-1148`). They do not identify which administrator-edited rules actually ran.
- Explanations independently hardcode CLB 8, two years, CAD 15,000, CAD 25,000, and ten months (`buildRecommendationRationale.ts:101-139,298-327,391-403`). Editing a DSL threshold to CLB 9 can leave text claiming CLB 8 is enough. Both evaluation and explanation must consume the same predicate result and parameters.
- Evaluation/results mutations remain writable after completion; their handlers do not require a nonterminal status (`convex/recommendationRuns.ts:1026-1073,1115-1149`). Lifecycle transition guards alone do not make a historical run immutable. Two concurrent starts can evaluate different rule revisions and overwrite artifacts while retaining one run ID.

### Ranking and composition safety

Alphabetical direct ordering gives the generic nominee category a higher score than skilled worker when both pass, independently of the user's intended province or priority. This is deterministic but arbitrary (`rankRecommendationCandidates.ts:181-188`). Do not describe these numbers as measured fitness or probability.

A target missing both a job offer and relocation gets the first matching composed string, such as `secure-valid-job-offer`; subsequent unmet requirements do not become graph preconditions (`generateComposedPathways.ts:46-53`). Composition supports only one result and no temporal state transition, budget feasibility, future program opening, status maintenance, or legal dependency check. Treat these as speculative improvement ideas until a real transition model is implemented.

### Test modes and fallbacks

The Nuxt boundary rejects nonstandard start modes and seed/reset routes only when `NODE_ENV === 'production'` (`testMode.ts:3-9`; start handler `:116-119`; testing seed `:39-42`; testing reset `:9-12`). This is a useful HTTP guard, but every other environment enables them automatically.

The **public Convex equivalents have no environment or auth guard**: `startProcessingForUser` accepts mock modes; `seedRunForUser` inserts supplied owners; `resetRunsForUser` deletes all rows for a supplied user (`convex/recommendationRuns.ts:1166-1206,1275-1305,1324-1334`). Consequently, the production HTTP check does not close the direct backend path.

The in-process fallback map has no environment guard (`testRecommendationRunFallback.ts:34-45,66-95`). Start/status/pathway/admin-review code can read it after backend failures. Normal production submission does not seed this map, so there is **no verified automatic substitution of a fabricated run for every real production run**. The risks are unguarded shared runtime code, test-data deployment/misconfiguration, error masking, process-local inconsistency, and broadened future exposure. Move all fixtures/fault injection to isolated test composition and exclude public seed/reset/mock exports from production deployment.

## 3. Correctness and safety architecture

### Authoritative rules graph

Use a **versioned, effective-dated domain graph**, implemented initially in PostgreSQL tables and typed TypeScript. A dedicated graph database is unnecessary. The essential property is a reviewed, replayable model of dependencies and transitions.

Proposed entities and contracts:

| Entity | Minimum fields / invariant |
| --- | --- |
| Jurisdiction / program / stream | Stable ID, official name, federal/provincial/Quebec owner, stage, parent, application route, coverage status, open/paused/closed status. |
| Rule release | Immutable release ID and digest, schema/evaluator version, valid/effective interval, recorded/published time, approver, superseded release, rollback target. |
| Criterion | Typed expression (`all`, `any`, `not`, threshold, table lookup, cohort, date window, exception), explicit missing-fact behavior, parameters/units, reason codes and supporting authority spans. |
| Reference tables | Versioned NOC/TEER and CIP codes, approved test conversions by skill, ECA equivalence, CRS/FSW point tables and family funds tables with effective intervals. |
| Draw / invitation event | Official round ID, scope/category, occurrence time, invitations, cutoff, tie-break and source snapshot; historical observation separate from future predictions. |
| Transition edge | Preconditions, resulting status/facts, duration/cost ranges and sources, expiry constraints, external decisions, uncertainty and forbidden assumptions. |
| Source snapshot / claim | Immutable bytes/hash, canonical URL, authority class, publication/observed/effective dates, exact passage offsets, acquisition/normalization version, approved/retracted state. |
| Evaluation receipt | Pseudonymous subject/profile snapshot, fact schema/hash, as-of time, rule-release digest, per-criterion input/result/reason, reference-table and source IDs, evaluator/ranker versions. |
| Review decision | Reviewer principal/role/license context, scope (rule/claim/run), immutable subject version, reason, time, expiry, decision and supersession. |

Track **legal effective time and knowledge time separately**. An announcement, a regulation's publication, its commencement, and an applicant's submission date may differ. A replay must answer both “what did we know then?” and “which rules applied to this application cohort?” Never apply today's threshold to an old application just because today's page was fetched recently.

Evaluation should produce `met`, `not_met`, `unknown`, and `out_of_scope` with a trace. Assess program eligibility separately from invitation competitiveness, documentary readiness, admissibility requiring professional review, and personal planning suitability. An unknown required fact prevents an unconditional eligibility claim. No active approved release or expired critical authority should yield a confident result.

For launch, implement and validate a **small named scope**, for example selected federal economic programs and one or two selected provincial streams. Choose the exact scope with an RCIC/lawyer. Quebec, family/business and complex status histories remain explicitly unsupported until modeled. Study-to-PR must expose each external decision and never imply that study guarantees PGWP or PR.

### Deterministic calculation and ranking

1. Validate all facts server-side, including dates, units, finite ranges, four language abilities, work periods/hours, NOC duties evidence, credential/ECA dates, family relationships and status periods. Keep unknown distinct from zero/no. The current permissive section records and presence check are insufficient (`intakeSchemas.ts:9,123-139`; `submit.post.ts:112-121`).
2. Calculate CRS and program-specific selection grids independently, with line-item receipts and effective-dated tables. Verify their totals against professionally curated examples and official criteria. Do not use old draw cutoffs as proof of an invitation or calibrated future success probability. [IRCC CRS criteria](https://www.canada.ca/en/immigration-refugees-citizenship/services/immigrate-canada/express-entry/check-score/crs-criteria.html).
3. Filter on eligibility/unknown status before ranking suitability. A ranking score should expose its components: timing, personal constraints, actual cost ranges, evidence completeness and preferences. If probabilistic estimates are later introduced, require measured calibration and cohort-specific limitations.
4. For composed routes, carry state over time: status, work authorization, education/program completion, language validity, available funds, age, application windows, budgets and mutually exclusive commitments. Every edge needs its own legal/operational preconditions. Use cycle/depth limits and reject impossible sequences. Return scenarios with unresolved milestones rather than guaranteed end states.
5. Derive rationale, blockers, actions and comparisons from evaluation traces and parameters. Preserve old receipts, and separately attach present-day usability warnings or revocation state; never rewrite history to appear current.

### LLM boundary

Allow an LLM to propose structured intake extraction, with field-level evidence, ambiguity flags and user confirmation. It may explain a completed decision trace or answer questions from admitted source passages. It must not create legal rules, invent missing facts, alter eligibility flags or infer authorization from prose.

Use explicit JSON schemas, pinned prompt/model versions, input/output limits, provider timeouts and an approved provider policy. Treat all retrieved content as untrusted data: it cannot change system instructions, request secrets or invoke arbitrary tools. Prefer templates for high-stakes eligibility explanations; if an LLM rewrites them, verify that every material claim maps to an existing trace/claim ID. Invalid or unsupported output falls back to the deterministic explanation, not to a more confident model.

Q&A retrieval must enforce current approval, tenant/visibility, authority level, effective interval and revocation **server-side**, regardless of what the client requests or the vector index still contains. Never index user profiles/documents into the public policy corpus. No private upload implementation was found in this checkout; architecture text proposing uploads is not evidence that privacy controls exist (`_bmad-output/planning-artifacts/architecture.md:164-169`).

### Citations, confidence and abstention

Current user citations are effectively disconnected: the generator never attaches evidence, candidate validators omit citations, and the result reader defaults missing citations to an empty array (`generateRankedRecommendations.ts:205-275`; `convex/schema.ts:106-156`; `readRecommendationResultsForUser.ts:241-249`). `classifyTrustBoundary` checks only citation count and metadata, not whether the citation supports the claim (`classifyTrustBoundary.ts:18-37`). Citation freshness uses a fixed 180-day window and even treats future retrieval dates as fresh (`buildRecommendationCitations.ts:35,63-75`).

Persist each material claim with source snapshot ID/hash, official URL, quoted passage boundaries, legal effective period, retrieved/verified times and reviewer. Fetch time alone does not prove policy currency. Record content authority, fact completeness and calculation support separately; use confidence labels only when their definition is testable. Missing/contradictory/expired required support yields “cannot assess” or “needs professional review.” Avoid a decorative number that sounds like immigration approval odds.

Admin review has a concrete false-support bug: `matchEvidenceSource` starts at -1, so a source with a score of zero can win; it never requires a positive match (`recommendationReviewService.ts:337-358`). The context loads all admin-visible sources, without filtering to current approved sources (`:555-572`). Fallback citation IDs/claims/URLs are synthesized (`:382-402,482-511`), and support can become strong from a mapped source plus high/supported metadata (`:273-295`). This is a governance projection, not actual evidence retrieval. Replace it with explicit missing-evidence records and exact snapshot linkage.

### Human review and accountability

Retain the existing review UI and reasoned flag/resolve workflow, but bind decisions to immutable rule/claim/run versions, professional identity, evidence and review expiry. A generic admin is not automatically an RCIC. Flagged/retracted support must suspend affected current user views and future evaluations until re-evaluated or explicitly reviewed.

Currently a flag only upserts PostgreSQL review state and writes a governance event (`server/api/admin/recommendation-reviews/[runId]/flag.post.ts:38-65`; `recommendationReviewStateService.ts:212-260`). The user results reader does not consult that state (`readRecommendationResultsForUser.ts:461-493`), so flagging a run does not withdraw its guidance. History/compare projections need the same current-admission check.

Before monetizing personalized advice, obtain a legal determination on the service/RCIC operating model. IRPA section 91 restricts advice or representation for consideration, and IRCC explains authorized paid representation. This review does not determine whether a particular software/business arrangement falls within those restrictions. [IRPA section 91](https://laws-lois.justice.gc.ca/eng/acts/I-2.5/section-91.html), [IRCC representatives guidance](https://www.canada.ca/en/immigration-refugees-citizenship/services/immigration-citizenship-representative/learn-about-representatives.html).

### Golden evaluation suite and publication gate

Maintain domain-owned fixtures containing the complete normalized profile, as-of/application dates, expected per-program outcomes, exact score breakdowns, missing facts, blockers, citation dependencies and reviewer rationale. Keep expected results independent of the code under test.

Initial coverage should include threshold minus/equal/plus cases, French/English alternatives, per-skill language differences and expired tests, incomplete/expired ECA, age birthdays, spouse/dependant and funds changes, continuous/noncontinuous and overlapping work, NOC/TEER exclusions, Quebec intent, stream closures, nomination/draw timing, study/PGWP cohorts and PAL exceptions. Include unsupported goals, malformed values, missing facts, impossible transitions and conflicting official sources.

For every policy release: validate schema/references/effective-interval overlap; run the golden suite on old and candidate releases; produce changed-profile counts and changed reasons; require professionally approved expected differences; run explanation/citation consistency checks; test fail-closed behavior with removed/expired authority; atomically publish one release pointer. Canary and rollback the pointer, retaining the failed release and its audit trail. Require deliberate negative tests that prove critical guards fail when disabled. For every new program add a positive case, a false-acceptance case and a false-rejection case before enabling it.

### Pipeline and admin triage

1. **Register authority and dependencies.** Extend existing sources with jurisdiction, official authority rank, document type, covered program/criteria IDs, expected check interval, freshness deadline, reviewer owner, acquisition permissions, locale and parser version. Source-level approval permits acquisition; it does not approve every future changed rule.
2. **Acquire safely and durably.** Queue bounded fetch jobs with conditional ETag/Last-Modified requests; archive response bytes, status/redirect chain, headers, fetch time, URL, SHA-256 and normalized text under immutable version keys. Support HTML, PDF, feeds and structured data; preserve tables, footnotes and bilingual differences. Use reviewed OCR only where needed. Current HTML-only rejection would skip PDF guides (`rag-ingestion-phase3.ts:409-419`).
3. **Diff and detect uncertainty.** Compare normalized semantic sections, numerical/date tables, links and structure. Separate layout noise from policy changes. Missing sections, parser failures, language disagreements, 404s and large deletions are alerts, not evidence that the old policy is still valid. Persist both versions and the diff. An LLM may summarize the change and suggest impacted criteria with cited passages, but cannot publish them.
4. **Open a policy-change case.** Store old/new snapshot IDs, detection time, claimed/evidenced effective date, legal status, affected criteria/streams, risk, assigned reviewer, due time, and disposition. Proposed states: detected → triaged → drafted → professionally approved → regression passed → scheduled/published → verified; also rejected/needs clarification. Retain reasoning for “no engine impact.”
5. **Contain risk.** An ambiguous high-impact closure or eligibility change suspends confident guidance for dependent programs while review is pending. Proposed operational targets: alert critical changes within one hour of detection and triage within one business day; these require staffing/on-call and must be agreed before being promised.
6. **Publish two controlled projections.** Approved content enters the retrieval corpus; approved typed rules enter an immutable rule release after the golden/regression gate. Keep a manifest connecting both to their source snapshots. A successful AI Search job is insufficient; run a retrieval probe that verifies the new snapshot and absence of revoked content.
7. **Propagate impact.** Dependency indexes locate affected active runs/claims. Preserve original receipts, attach “policy changed / needs refresh,” suppress unsafe current actions, and offer a new run comparing rule changes separately from profile changes. User notifications require a product-owned consent and delivery policy.
8. **Measure coverage and recovery.** Dashboard missing sources, overdue checks/reviews, parser errors, source-to-index lag, rejected diffs, authority age and impact backlog. Reconcile database/object/index manifests and retry from durable checkpoints.

### Admission, revocation and ingestion-specific risks

- Pausing a source changes lifecycle state but does not delete its R2 objects or prove deindexing. Source removal deletes Convex source/items and approval audit records without R2/index cleanup (`ragSourcesInternal.ts:248-276`). The public query proxy does not recheck source state. Add revocation tombstones and admission filtering immediately; background deindexing is an additional control.
- `respectRobots`, `renderMode`, and `requestHeadersRef` are accepted and normalized but not used by website execution (`rag-ingestion-phase3.ts:489-521,2508-2690`). Either implement their contract or refuse unsupported configurations. Preserve the current bounded depth/page checks, adding per-origin throttles and response-byte budgets.
- Redirects are automatically followed; the final hostname is checked only after fetching (`:357-369,419-420,2580-2587`). The per-source domain list is configurable, not a global public-network safety policy. A malicious/compromised approved source can redirect into private/local services before rejection. Enforce HTTPS/public address policy, DNS/IP checks and redirect revalidation before each outbound request, with egress restrictions where possible. This is a static SSRF scenario; network reachability was not tested.
- The website timeout is cleared once `fetch` returns headers, before `response.text()` reads the body (`:357-369,419`). Bound full-response duration and bytes. AI Search/sync/R2 fetches have no explicit request timeout in their wrappers (`cloudflare-ai-search.ts:146-156`; sync `:68-77`; `rag-storage.ts:146-150`).
- YouTube Data API is used for video discovery (`rag-ingestion-phase3.ts:1112-1145`), not guaranteed arbitrary transcript download. Transcripts try InnerTube Android, watch-page captions and an external transcript service, then can fall back to descriptions (`:2172-2217`). A public third-party transcript endpoint is the default (`:1464-1466`). Timestamps and provider/fallback metadata are preserved (`:2361-2409`), which is useful, but descriptions must never count as transcript-backed evidence.
- Official Google documentation distinguishes public-metadata API keys from OAuth/private access and reports insufficient-permission failures for caption downloads. Retain acquisition permission/provider records and prefer licensed/authorized transcripts. No finding here establishes whether a particular source's use is lawful. [YouTube authorization](https://developers.google.com/youtube/data/guides/authentication), [caption download errors](https://developers.google.com/youtube/data/reference/rest/v3/errors).

## 5. Security, privacy and operational gaps

### Authorization inventory and IDOR assessment

A static census found **54 handwritten server API route files**: 36 admin routes call `requireAdminSession`, 16 intake/recommendation/workspace routes call the workspace-session guard, one internal scheduler checks its shared secret, and one AI-search route has no local auth guard. This does not include module-generated Better Auth endpoints or prove runtime configuration of them. No global server middleware was present to compensate for the unguarded AI route.

The Nitro run routes generally derive `userId` from the session and pass it with the run ID. Comparison first finds both runs in that user's list, and SQL snapshot reads include owner predicates (`server/api/workspace/runs/compare.get.ts:66-85`; `evaluatePathwayEligibility.ts:49-55`). **No run-ID-only Nitro bypass was established in these reviewed paths.** The critical IDOR is at the independently callable Convex layer: caller-supplied ownership values are compared with stored values without a trusted caller identity. The cross-user listing removes any need to guess UUIDs.

RAG public functions demonstrate a better pattern: `requireIdentity`, admin-table lookup and `requireAdmin` protect source reads/mutations (`convex/ragSources.ts:46-94,219-227,255-264,382-383`). Public bootstrap is explicitly disabled (`:200-204`). Ingestion and privileged source lifecycle functions are internal (`ragIngestionInternal.ts:1-2`; `ragSourcesInternal.ts:1-2`). Preserve these protections while adding tenant membership and immutable-principal role checks where needed; user-provided `tenantId` is metadata, not authorization.

`convex/auditLog.ts` also exports unauthenticated public recording/list/detail/summary functions (`:59-110,189,222`). This permits fake audit actors/timestamps and exposure of any data stored there. The **active governance writer uses a separate PostgreSQL `governance_audit_log`**, so this is not evidence that the same public mutation can rewrite that SQL log (`server/utils/audit/recordGovernanceAction.ts:16-31`; `auditLogStore.ts:172-196`). Remove the unused public scaffold or protect it and choose one authoritative audit ledger.

### Admin grants and session controls

Admin authorization can come from `rag_admins` or an explicitly allowed environment list. The allowlist accepts user ID **or email**, with no `emailVerified` condition (`requireAdminSession.ts:12-16,36-55`). Convex similarly accepts email matches from `rag_admins` (`ragSources.ts:61-79`). The server auth config only enables password authentication and the Convex plugin; it does not configure email verification/MFA/reset delivery (`server/auth.config.ts:5-12`).

**High-risk inference:** if an allowlisted email has no existing account and normal sign-up permits an unverified session, someone registering that address could receive admin access and persist the grant via sync (`server/api/admin/rag/convex-admin/sync-current-user.post.ts:5-19`). Current Better Auth documentation describes verification as an explicitly configured flow; the exact resolved alpha-module behavior was not run. Gate admin grants by verified immutable principal IDs, require MFA/step-up for policy publication/deletion, and test sign-up, email change, account linking and revocation. Removing an email from environment config alone does not revoke an existing `rag_admins` row. [Better Auth email verification](https://better-auth.com/docs/authentication/email-password).

The scheduler correctly fails closed on a missing secret and rejects a mismatched value (`daily-ingestion.post.ts:38-53`). It has no signed timestamp/replay window; the caller can supply idempotency keys and `force` (`:56-68`). Retain idempotency, add secret rotation and authenticated scheduled workload identity or signed/replay-bounded requests, plus queue/spend limits. No checked-in scheduler deployment proves the daily endpoint is actually invoked.

Ordinary recommendation/intake operations use a Convex admin key (`server/utils/convex-admin-client.ts:34-59`), increasing blast radius if the Nitro app is compromised. Prefer scoped user JWTs for public user queries and internal workflow capabilities for server writes. Avoid adding new arbitrary impersonation sites around `setAdminAuth` (`:62-76`). Review canonical origins/forwarded-host trust because token minting constructs its URL from the incoming request origin and forwards cookies (`:81-91`). No host-header exploit was established.

### Privacy and Canadian residence

Profiles are stored as JSONB without application-level field encryption (`submit.post.ts:217-231`); this does **not** establish whether managed disks/backups are encrypted. Provider transport is generally HTTPS, while default local auth URLs are development values. Verify TLS, at-rest encryption, key ownership/rotation and privileged support access across the deployed stack.

No complete user export, account deletion workflow spanning stores, retention scheduler, consent ledger or privacy-request process was found. The profile foreign key has SQL `ON DELETE cascade` (`server/db/migrations/postgresql/0002_recommendation_profiles.sql:1-6`), but Convex only stores string user IDs and does not participate in that cascade (`convex/schema.ts:159-197`). PostgreSQL deletion alone leaves Convex runs, review state and potentially logs/backups. A testing reset endpoint is not a production privacy lifecycle.

PIPEDA does **not** create a blanket requirement to keep all private-sector data in Canada; its cross-border guidance makes the organization accountable for protection and contractual safeguards. Quebec adds relevant privacy impact assessment and transfer obligations. Determine applicability based on actual users, business activities and contracts. [Convex regions](https://docs.convex.dev/production/regions), [R2 data location](https://developers.cloudflare.com/r2/reference/data-location/).

Keep the public-policy corpus separate from customer data.

### Observability, reliability and error handling

Useful pieces exist: stored lifecycle states/heartbeat fields, source-run counters/error codes, sync job IDs/log summaries, and some structured ingestion logging (`convex/schema.ts:167-193,378-442`; `rag-ingestion-phase3.ts:384-390`). These do not constitute end-to-end monitoring or recovery.

Recommendation start does multiple sequential remote calls and SQL reads in one request. After `evaluating`, process loss or a failed final-status write can leave a run stranded; failure-status writes are swallowed (`start.post.ts:281-295,327-341`). The heartbeat is written on state mutations, not maintained by an independent worker lease (`convex/recommendationRuns.ts:1200-1206`). Repeating start on terminal failed runs returns them unchanged (`start.post.ts:229-247`). There is no demonstrated automatic retry/reaper for stranded runs.

Ingestion similarly loops through all prepared sources in one request (`rag-ingestion-phase3.ts:2760-2825`), and sync polls for up to 90 seconds without per-fetch timeouts (`cloudflare-ai-search-sync.ts:294-345`). Reused batch requests do not resume execution (`daily-ingestion.post.ts:74-79`). Retry scaffolding only writes `nextRetryAt`; it explicitly states automatic retry execution is unimplemented (`ragIngestionInternal.ts:1146-1177`).

Implement durable at-least-once jobs with atomic claims/leases and fencing, idempotent stage keys, bounded exponential retry/jitter, provider Retry-After handling, circuit breakers, dead letters, stale-job reconciliation, and separately retriable finalization. Use an outbox or a single authoritative transactional store for profile submission and job creation; do not rely on in-request compensation as distributed atomicity. Reconcile object write success, DB manifest writes and indexing after crashes. A later provider success must not overwrite a newer attempt or revoked release.

Missing R2 credentials select `local-fallback` even in production (`rag-storage.ts:162-173`). On ephemeral/multiple instances, data can be lost or never indexed while metadata advances. Require cloud storage configuration at startup in production and reject unsupported storage modes. The phase-0 readiness endpoint checks configuration presence, explicitly deferring endpoint behavior (`rag-foundation.ts:150-190`); it does not validate R2 connectivity, DB region, permissions, provider schema, ingestion freshness or retrieval.

Add trace IDs connecting request → profile/run/release → job/attempt → evidence snapshots → provider request → result. Log codes, duration, counts, versions and pseudonymous references; redact profile bodies, cookies, tokens and raw prompts. Add metrics/alerts for authorization failures, submitted/finished/stranded runs, confidence/abstention shifts, freshness/review backlog, ingestion lag, parser failures, sync lag, DB bandwidth/read counts, provider errors and budget exhaustion. Use real synthetic profiles in isolated accounts to test the complete workflow.

Proposed launch targets, to be measured before commitment: 99.9% API availability; p95 deterministic evaluation under five seconds after accepted submission for the launch catalog; queue-age/stuck-run alerts within five minutes; monitoring sources within their declared cadence; initial recovery objectives of RPO ≤24 hours and RTO ≤4 hours for a small pilot. A professional owner must decide stricter objectives for real client work. These are proposals, not current performance results.

### Convex performance and scalability

The three-item evaluator itself is inexpensive. Present scaling risks come from access patterns and orchestration:

- `listForUser` loads every run for a user; `listForAdmin` scans every full run, sorts and only then applies `limit` (`convex/recommendationRuns.ts:933-962,1377-1413`). Add indexed cursor pagination and separate small list summaries from result/trace documents.

Use a transactional idempotency key/unique lookup and enforce refresh lineage; do not depend on unguessable random IDs to prevent attacker-chosen duplicates.

## 7. Technical debt and simplification

Measured at this commit: `server/utils/rag-ingestion-phase3.ts` **2,832 lines**; `convex/recommendationRuns.ts` **1,453**; `app/pages/workspace/intake.vue` **1,325**; `recommendationReviewService.ts` **827**; `buildRecommendationRationale.ts` **690**. Length is a maintenance signal, not a defect by itself; the substantive problems are mixed responsibilities and diverging sources of truth.

Prioritize these changes alongside the safety work:

1. **One decision contract.** Put pure fact schemas, criterion results, scores and reason codes in a shared domain module. Convex currently duplicates validators/normalization/templates also represented in server/app code (`convex/schema.ts:15-156`; `convex/recommendationRuns.ts:118-254`; `rankRecommendationCandidates.ts`; `buildRecommendationRationale.ts`; `app/lib/recommendations/comparison.ts`). Generate persistence/API contracts or use narrow adapters around one model; avoid reinterpreting confidence at each read.
2. **One active rule representation.** Migrate seeds through release tooling, remove runtime CREATE TABLE/seeding from read paths, retire in-code fallback rules from production, derive explanations/composition from criterion traces. Keep the legacy catalog only as explicitly labeled fixtures during migration.
3. **Narrow ingestion modules.** Split acquisition/network safety, HTML/PDF/feed parsing, YouTube discovery/transcript adapters, normalization, immutable storage, item persistence, orchestration and sync reconciliation. Preserve provider/fallback provenance. Defer YouTube to a secondary explanatory corpus for the first release; official policy coverage has higher decision value.
4. **Simplify persistence deliberately.** PostgreSQL already owns auth, profiles, inventory/rules, review state and active governance audit; Convex owns runs/sources/jobs. For the pilot, either retain Convex behind a clear internal operational boundary with an outbox/reconciliation contract, or consolidate workflow/run state in PostgreSQL plus one durable job mechanism. Consolidation can reduce credentials and dual-write/deletion complexity, but is not a prerequisite rewrite if it delays the urgent authorization fix. Decide after measuring needed realtime features. Do not add a third workflow store.
5. **One audit/review model.** Remove/secure the public unused Convex audit scaffold; make governance mutations and their SQL audit records transactional where co-located, with an outbox for external work. Preserve source tombstones and audit history instead of deleting approval audit rows on source removal. Current rule writes and subsequent route-level audit writes are separate (`rules.put.ts:40-59`).
6. **Reduce page-local duplication.** Move intake field definitions, server validation contracts and section progress logic out of the large page into shared schemas/components/composables. Keep server validation authoritative. Consolidate repeated auth/session test setup and fixture building; keep actual end-to-end paths distinguishable from mocked UI stories.
7. **Remove launch-facing demos.** `/ai-search` is an unguarded playground (`app/pages/ai-search.vue:1-48`), and `tasks.client.vue`/`convex/tasks.ts` are wiring demos; the latter reads identity but does not reject missing identity (`convex/tasks.ts:4-24`). Remove them from the production surface or make the playground explicitly admin-only with quotas.
8. **Refresh operational docs to match source.** `docs/architecture.md:67-78` and `_bmad-output/project-context.md:56-63` say no test framework exists, while package/config/tests prove otherwise. `docs/deployment-configuration.md:9-15` says no CI definitions exist despite `test.yml`. Planning architecture calls for immutable runs, versioned rules, async orchestration and structured monitoring (`architecture.md:169-184,209-210,235-239`), but those decisions are not evidence of implementation. Keep a short implemented/planned/unsupported matrix with release evidence.
