### Encryption and scoped downloads

S3 encrypts new uploads with SSE-S3 by default; optional SSE-KMS supports customer-managed key policies, rotation and auditing, with keys in the same region as the bucket and additional charges. GCS encrypts at rest by default and supports CMEK with matching key-location restrictions. Azure encrypts storage by default and offers customer-managed Key Vault/HSM keys and encryption scopes. B2 supports SSE-B2/SSE-C; enable the bucket default before uploads because changing it does not encrypt existing objects. OVHcloud documents the same existing-object caveat for enabling SSE-OMK.[^aws-kms][^gcs-keys][^azure-keys][^b2-security][^ovh-security] **Recommendation:** start synthetic staging with provider-managed encryption unless the architecture decision requires CMK; do not call that end-to-end encryption. The scanner and authorized server still need plaintext access. Key selection must include backup/restore and scanner permissions, not only “encryption enabled.”

### Upload limits, types, and malware scanning

**Proposed pilot envelope for #41:** PDF/JPEG/PNG only; 1 byte–10 MiB per file, 25 files and 250 MiB total per Client, two concurrent uploads, immutable random object keys and server-side quota reservations. These are conservative engineering defaults for synthetic staging, not settled owner limits or provider ceilings. The app must enforce actual bytes while streaming, extension/signature/type consistency, final size/checksum and authorization at upload admission **and** completion. Client MIME and an HTML `accept` attribute are not security controls. Reject archives, encrypted/password-protected documents, executable formats, unexpected HTML/SVG and unsupported scan outcomes; abandon partial uploads on timeout. OWASP recommends allowlists, byte limits, generated names, authorization and antivirus/sandbox checks.[^owasp]

AWS POST policies support exact object keys, Content-Type conditions and `content-length-range`; OVHcloud documents a corresponding POST policy. A Content-Type match constrains the submitted declaration, not the true file type. For direct-to-storage ingestion, use private quarantine plus post-upload validation and delete invalid/orphan objects. R2's form POST is unsupported. Convex's generated upload URLs accept arbitrarily large files, so choosing its direct upload route alone does not enforce the proposed cap; use a bounded authenticated server route or prove an equivalent admission/control mechanism.[^aws-post][^ovh-post][^r2-url][^convex-upload] S3 currently documents a 5 GB single-PUT and 50 TB object ceiling; these service maxima are irrelevant to the smaller proposed product cap.[^aws-faq]

### Deletion, recovery, audit, and costs

**Verified deletion traps:** S3 simple DELETE on a versioned bucket creates a delete marker; remove each version explicitly for erasure. GCS default seven-day soft delete can be disabled with duration zero, but changing the policy does not shorten retention for already-deleted objects. Azure blob soft-delete retention is 1–365 days and disabling it does not purge previously soft-deleted objects. B2 lifecycle rules distinguish hiding from deleting versions. OVHcloud versioned expiration also creates markers; lifecycle execution is asynchronous. Convex backups may include files; documented manual/daily retention is seven days and weekly retention fourteen days, with periodic backups on Pro. The Convex backup FAQ separately says each backup is accessible up to seven days, an internal documentation inconsistency to clarify for weekly backups.[^aws-delete][^gcs-delete][^azure-delete][^b2-delete][^ovh-delete][^convex-backup]

S3 Object Lock can prevent deletion/overwrite for a retention period or legal hold, including an indefinite hold.[^aws-lock] **Recommendation:** leave raw-upload vault objects outside WORM/retention locks unless #36 explicitly defines the need and the resulting deletion exceptions. Keeping a Signed plan record does not automatically require locking the source uploads.

**Proposed contract:** distinguish access revocation, live-object deletion, recovery-copy expiration and provider media erasure. Maintain an idempotent deletion manifest covering metadata, current/noncurrent objects, quarantined copies, derivatives, incomplete uploads, caches, scanner scratch, exports and backups. A failed provider delete remains pending/retrying and inaccessible; do not report completed erasure from a database-row deletion or a 404 on the latest version. Apply tombstones before restoring any backup to prevent deleted files or revoked sharing from reappearing. Keep raw Client uploads separate from retained Signed plans/audit so the settled Practice retention rule does not become blanket retention of every uploaded document.[^map][^aws-delete][^convex-backup]

Store a minimal application audit of admission, completion, scan, access allow/deny, sharing revocation, deletion attempt/result and restore reconciliation, using opaque IDs. S3 access logs can go to a bucket in the same region/account, but delivery is best effort; this is supplemental evidence, not the sole audit trail. GCS log regionalization needs independent configuration. Operational log retention must be finite and specified by #36/#45; bucket region alone does not select it.[^aws-logs][^gcs-logs]

Relevant usage types are `CAN1-TimedStorage-ByteHrs`, `CAN1-Requests-Tier1`, `CAN1-Requests-Tier2`, `CAN1-MalwareProtectionS3DataScanned`, and `CAN1-MalwareProtectionS3ScanRequest`. Azure's public retail feed identifies Canada Central Hot LRS storage meter `627916dd-3eb1-4b1d-bd1c-9f19593f6d25` and Hot ZRS `9651b232-5889-4d7f-8fee-7cfcc739bda0`; zero-tier rates are used above.[^aws-price][^aws-scan-price][^azure-price]

**Illustrative calculation, not a quote or budget approval:** 10 GB-month S3 Standard + 1,000 uploads + 1,000 GETs + 10 GB scanned costs about **$1.54/month** before network, logs, tagging, keys, compute and other services, conservatively ignoring free allowances: `10×0.025 + 1×0.0055 + 1×0.00044 + 10×0.1035 + 1×0.246 = 1.53694`.
