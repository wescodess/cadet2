# System of record for portal data

Decision date: 2026-11-17. Baseline: `dev` at `fe2b4a4e4f8b4b861fb5c92661b9e411a84ef0b3`. Resolution: **answered-on-auto**, with the owner gates below still open. This records the answer to [Decide the system of record for portal data](https://github.com/wescodess/cadet2/issues/33) under [Chart the Client and Representative portals for a staging pilot](https://github.com/wescodess/cadet2/issues/29).

## Decision and scope

**Convex is the single system of record for portal data: the official Better Auth Convex component owns identity/auth, and application Convex tables own Practice authority, Client profiles, Case work, consent, assessment snapshots, Signed plans, audit, document metadata, reminders, and pathway/rules administration.** There is no ongoing application SQL database or Postgres host in the selected target. Domain writes must not span SQL and Convex. [Decide Practice tenancy and authorization boundaries](https://github.com/wescodess/cadet2/issues/34) specifies the supported auth integration, versions and authorization contract using [Research auth wrapper and Practice membership compatibility](https://github.com/wescodess/cadet2/issues/32); it does not need to choose data ownership again.

This is a target architecture, not a claim that today's Nuxt integration supports it. Choose exactly one auth authority per environment at cutover; a login must never search both credential stores. SQL retirement waits for a verified migration. If the tenancy decision establishes that component-backed auth cannot meet the proof gates, bring that evidence back to this decision before adopting the considered **Canadian SQL-auth-only** alternative. That is a bounded revision option, not an automatic runtime fallback or permission to move domain records back into SQL.

The destination remains a private design-partner pilot on staging with synthetic data. Canadian placement is settled for every Client-data environment. Production launch, real Client data, billing, an engine rebuild, and portal LLM features remain outside this decision. Paid hosting/storage/email services are recommendations pending owner approval; no account, purchase, deployment, region creation, migration, or data deletion is authorized here. The architectural rationale is recorded in [ADR 0002](../adr/0002-convex-portal-authority.md), numbered after the already published [assessment evidence ADR 0001](https://github.com/wescodess/cadet2/blob/a00154ce37cfaa021747fcfd57be14fdbe17bb02/docs/adr/0001-preserve-assessment-evidence-boundaries.md).

## Evidence and language

The settled owner destination and the map take precedence over older planning. The owner's stack defaults favor Convex/Cloudflare where sufficient and near-zero running cost. [Canadian hosting research](https://github.com/wescodess/cadet2/blob/2fb55b2b63143cddad44252b249a2b05d237e5b1/docs/research/canadian-hosting-and-databases.md) was read in full. It establishes Canadian Convex availability, not a complete Canadian contract for telemetry, backups, or support. Cloudflare's default Workers/Pages, D1, R2 and Hyperdrive cannot supply the required Canadian boundary; Supabase's Canadian database leaves an explicit EU operational-log conflict. Keep both out of the Client-data route on those assumptions.[^hosting]

The glossary was read from `origin/docs/portals-map` at `5995648771b1017230886a8a0c14670e9f152ec9`; this branch remains based on `dev`, without importing that branch. No newly resolved domain term requires a glossary edit. In particular:

- A Client owns their account and profile. A Practice does not own that identity or gain every profile revision through membership alone.
- A Case is one Client's matter at one Practice. Solo utilities are Client-owned records, not Cases at a fabricated Practice. Sharing the same Client across two Cases never merges their consent or working records.
- A Draft assessment is private work for professional review. A completed legacy recommendation run is not a Signed plan, and an admin review flag is not a Representative's signature.
- Practice retention of Signed plans and audit after consent revocation is a separate authority from access to the Client's current profile, intake, or vault. It grants no continuing blanket access.

The glossary and settled map already define these distinctions.[^glossary] Exact role permissions, consent scope, retention periods, lifecycle states and signature evidence belong to the existing tenancy, consent, lifecycle and verification decisions; storage placement does not settle those policies.

## Authority and residency by data class

**C** below means the environment's isolated Convex deployment, required to be in Canada. **A** means its Better Auth component in that deployment. **O** means a private Canadian object store with Canadian upload/download/scanning execution; it may be Convex file storage or an approved external byte store, while C remains the metadata authority. Placement covers cadet2-controlled services/copies; it does not establish a recipient's device or mailbox location. No existing deployment, bucket, log sink or backup location has been verified. The table states required placement, not an observed deployment guarantee. The managed Convex candidate is `aws-ca-central-1`; region creation is owner-gated and immutable. Free has regional selection; billable Canadian usage has a 30% surcharge, so free-tier operation is not a promise of unlimited or permanently free service.[^hosting][^regions]

| Data class | Authoritative store and boundary | Required residency and permitted copies |
| --- | --- | --- |
| Identity/auth | **A**: Better Auth users, credential/account links, sessions, verification/reset tokens and JWKS. No credentials, session tokens or private keys in domain tables. | Canadian auth execution and persistence; keys/secrets, rate-limit state, backups and logs enter the same inventory. A minimal Convex principal binding is a reference, not a second credential store. |
| Practice, membership, invitations and Representative verification | **C**, application-owned records. Membership/verification grant authority; auth claims and an active-Practice cookie do not. Invitation state includes expiry, intended scope, single consumption and delivery intent. | Canada, including invitation outbox and verification evidence. Email carries only the approved minimum invitation/auth material. A component organization plugin, if selected later, must have one authoritative membership model, not a competing grant ledger. |
| Client profile and solo utilities | **C**, keyed to the Client's principal independently of any Practice. Corrections produce a new current revision. | Canada. Case-specific sharing uses explicit snapshots/references and current consent; a Practice receives no global profile replica. |
| Case | **C**, with immutable Practice and Client associations and an application revision. A transfer needs the lifecycle/consent contract rather than changing ownership silently. | Canada. Lists and counts are rebuildable, permission-filtered projections. |
| Intake | **C** for editable intake and immutable submitted snapshots. Submission binds the exact intake/profile revision to the intended Case, or to a solo utility operation that does not expose unsigned personalized output. | Canada. Case submissions retain their scope; editing the Client's current profile does not mutate old submissions. |
| Draft assessment and professional edits | **C** for run state, input snapshot, exact consumed rules, calculation receipt, citations/source dates, result and edit revisions. Work is attached to its Case and attempt. | Canada, including worker scratch/logs. Client projections exclude unsigned personalized content. Public-information content is separately classified. |
| Signed plan and signature | **C** for the immutable signed payload, its input/result/edit references and signer/licence/date/rule/source evidence. An exported PDF is a rendition, never the authority. | Canada; any stored rendition uses **O** with a version/checksum reference in C. Practice-retained records are separated from deletable live profile/vault records. |
| Consent | **C** for grants, revocations, scope, revision and audit. A pending invitation or valid session is not consent. | Canada. Cached consent or copied JWT claims cannot authorize access; retained-record rules are checked separately. |
| Audit | **C** for authoritative Case and governance events, committed with the state transition they attest. Historical SQL governance events retain their original provenance on import. | Canada. Minimal actor/evidence snapshots and restricted retention; operational logs are supplemental, never a substitute ledger. |
| Documents metadata and sharing | **C** for owner, Case sharing grants, storage/version identifiers, actual size/checksum/type, scan result, lifecycle, quota reservations and deletion receipts. | Canada. Raw bytes/quarantine/scanner scratch/versions are in **O**; object ACLs, tags or a download URL do not grant Case authority. |
| Reminders and delivery state | **C** for source dates/timezone, schedule revision, consent/preferences, occurrences, suppression, outbox, attempts and delivery receipts. External email is an effect of this state. | Canadian scheduling/execution and capture sink. A live provider must separately prove its complete permitted boundary; a Canadian API endpoint alone is insufficient. |
| Pathway/rules administration and review state | **C** for definitions, status, ordered rules, admin edits, source/trust links, run/citation review states and corresponding governance audit. | Canada, including identifying admin/audit data. Public policy text may be public, but linking it to a Client, Case or actor makes that record subject to this boundary. |

Opaque technical identifiers, version numbers and hashes are storage contracts, not new domain vocabulary. Use a stable application principal ID bound uniquely to `(environment, trusted issuer, auth subject)`, never an email address. Preserve old user IDs through an explicit alias map if auth subjects change. Use stable Practice, Case, snapshot, run, Signed plan, document and occurrence IDs; retain legacy `snapshotId`, `runId`, `sourceRunId` and refresh-lineage references as aliases. Imports use `(source store, table, original ID)` keys, so different stores' event IDs cannot collide. Convex indexes do not replace transactional uniqueness checks.

Every Case-owned record carries or resolves its Practice/Case/Client scope, and every backend read/write validates the relationship from stored records. A caller-supplied `userId`, `practiceId`, `caseId`, role, object key, signature or owner claim is never authority. A principal may be a Client and a Practice member without conflating those rights. [Decide Practice tenancy and authorization boundaries](https://github.com/wescodess/cadet2/issues/34) supplies the detailed permission matrix and trusted-call contract.

Allowed projections are bounded portal DTOs, lists/counts, notifications and export renditions that record their source IDs/revisions and environment. They cannot become permission or signature authorities. Recheck the applicable live grant or retained-record rule on history, search, export and download; include membership/consent/session revisions in live-query dependencies so revocation invalidates subscriptions. Partition caches by principal, Practice/Case and revision, clear them on account/Practice switching, and deny or rebuild stale projections. Private responses must not enter shared CDN caches; unsigned personalized content must never enter a Client projection. There is no durable offline Client-data replica in the pilot storage contract.

## Why this shape

| Alternative | Genuine advantage | Cost or risk and disposition |
| --- | --- | --- |
| Convex domain plus Better Auth component | One regional persistence platform; removes Postgres hosting, SQL-auth backup coordination and the intake/run split. Live component session lookup can accompany domain authorization. | Selected technical target, subject to implementation proof before activation. Requires migrating all SQL-held data, rewriting SQL repositories and proving the Nuxt boundary. Component limits, schema maintenance and application-enforced references/uniqueness replace SQL constraints. |
| Convex domain plus SQL auth | Preserves SQL identity IDs, schemas and adapter storage while domain work becomes transactional in Convex. | Not selected: requires a corrected token bridge anyway, a Canadian SQL runtime/store, another backup/restore surface, principal synchronization and a proved session-revocation bridge. It remains a credible revision option if component integration is disproved, with no domain grants or Case data in SQL. |
| Postgres for auth and all domain data | SQL constraints, joins and a single SQL transaction could cover Case state, snapshots, audit and an outbox. It preserves existing SQL admin repositories. | Rejected for this effort: moves the existing Convex run/operational authority and new portal backend toward SQL, retains Canadian SQL hosting, and abandons the preferred backend without a demonstrated requirement. This is technically viable; residency does not force Convex. Revisit only with measured requirements the chosen shape cannot meet. |
| Keep the current SQL/Convex domain split | Least immediate repository churn. | Rejected: snapshots/runs, rule edits/audit and reviews/results remain separately committed, separately restored and separately deleted. Keeping SQL solely for pathway definitions or governance audit prevents SQL retirement even if auth moves. |

This accepts a larger one-time migration to reduce continuing services and consistency boundaries. The auth research means both auth-store alternatives require deliberate integration work; retaining the unchanged SQL bridge is not a safe shortcut. Moving auth is justified by removing that continuing SQL service, not by needing an organization plugin. It does not assume arbitrary workloads fit a single Convex document or transaction: use indexed, paginated access and bounded work units; split large immutable artifacts behind a manifest, and publish only after the complete manifest is sealed. Do not introduce SQL reporting/search replicas for the pilot. Measure transaction size, storage, I/O and scheduling headroom before capacity claims.

## Auth-integration seam for the tenancy decision

At baseline, NuxtHub supplies the SQL database to `server/auth.config.ts`; its Convex plugin mints tokens, while `convex/auth.config.ts` trusts the site's issuer/JWKS endpoint. There is no `convex/convex.config.ts` mounting the Better Auth component. NuxtHub uses local PGlite without a database URL and PostgreSQL when one is supplied. Installing `@convex-dev/better-auth@0.10.11` did not relocate auth data.[^auth][^hosting]

The official component at the pinned release contains `user`, `account`, `session`, `verification` and `jwks` tables, and exposes `authComponent.adapter(ctx)`. Its declared Better Auth peer range includes the baseline's `1.4.9`, and its Convex range includes the lock's `1.32.0`; that is static compatibility evidence only. Its shipped schema does not include Practice memberships/organizations. Component session lookup checks live session existence/expiry; JWT identity verification alone does not do that. Triggers are atomic with the individual database operation, but a single Better Auth endpoint can perform several separately committed operations.[^component-schema][^component-package][^component-client][^component-triggers]

The exact Nuxt wrapper package, `@onmax/nuxt-better-auth@0.0.2-alpha.29`, supports custom database-provider registration and a server-config database override; its default enabled NuxtHub provider generates a Drizzle adapter. That is an extension point, not proof that a Nuxt request has the Convex context required by the component. Current online component guides describe later releases and cannot validate the pinned combination.[^wrapper]

[The resolved auth research](https://github.com/wescodess/cadet2/blob/d86665738faf2222dd0b201e7a7dec48286ed720/docs/research/auth-wrapper-and-membership.md) supplies a reproduced pinned-stack failure: after `/get-session`, sign-out returns 200 but leaves the SQL session usable for token minting. Its standard Better Auth `jwt()`/Convex custom-JWT control restores SQL renewal/deletion and rejects retained-cookie minting. These are supplied isolated PGlite/package results, not a browser/Nitro/staging reproduction run in this decision. The existing [Security: sign-out leaves a usable session through the Convex auth bridge](https://github.com/wescodess/cadet2/issues/53) owns the implementation fix. Keeping the current component-oriented plugin on SQL unchanged is excluded; upgrading that plugin alone is not a supported SQL-bridge proof.[^auth-research]

The tenancy decision must settle the remaining seam from that research:

1. Choose maintained, mutually compatible package versions and prove a narrow Nuxt/Convex auth topology: request routing, authenticated SSR/cookie forwarding, sign-up/sign-in/sign-out, verification/reset, token renewal, issuer/audience/JWKS rotation, callback origins, and direct Convex session expiry/revocation. The pinned component is evidence of baseline capabilities, not a supported-version recommendation. A Canadian Nuxt proxy to Convex-hosted auth is an option to evaluate. No arbitrary admin impersonation or request-derived trusted issuer.
2. Keep Practice membership, Case grants and consent authoritative in application Convex tables. If an organization plugin changes that representation, demonstrate one atomic authority and equivalent authorization checks, including Staff/Representative separation. Installing a plugin cannot grant the signing role or verify a licence.
3. Prove auth migration: subject/ID mapping, credential-hash compatibility, account links, date units, email uniqueness/verification, JWKS/issuer changes, export/deletion and isolated restore. Do not copy active sessions or outstanding verification/reset tokens as if they remained valid. A fresh login after controlled cutover is safer; preserving passwords still requires a verified migration path. Existing users must not be recreated by matching email alone.
4. Activate component-backed auth only after proof passes and the separately authorized cutover completes. Failed proof keeps activation blocked and must name the failed requirement before a decision revision; it does not silently select SQL. If SQL-auth-only becomes necessary, the researched standard Better Auth JWT/custom-JWT bridge still needs live-session validation/revocation and direct-backend tests. A short-lived JWT alone is insufficient proof of immediate session revocation. An unavailable session check denies access; it does not fall back to an unchecked bearer token.

This integration seam does not defer the storage decision. The target is not proved end to end. Component-hosted organization tables require Local Install and schema generation; that is independent of moving auth, and is unnecessary merely to keep application-owned Practice authority in C.[^auth-research]

## Transactions, external writes and recovery

The following are requirements for future delivery, not capabilities supplied by this documentation change.

### Domain operations

An intake submission checks the current principal, Case association, live membership/consent where applicable and expected intake revision, then commits the immutable input snapshot, assessment-run intent, audit event and queued work in **one Convex mutation**. Take the exact consumed pathway/rule snapshot in that transaction. Use a client-operation key scoped to principal, Case and action: the same key and input returns the original IDs; a different input under the same key conflicts. A lost HTTP response must not create a second submission on retry.

Evaluation is bounded asynchronous work against that immutable snapshot. Claim an attempt with a lease/fence; result finalization must match the run, input/rule snapshot, attempt and still-permitted Case authority. A delayed older attempt cannot replace newer work. Schedule durable work as part of the committing mutation, retain business job state beyond scheduler logs, and reconcile stranded/expired attempts with bounded retries. Auth is not inherited by scheduled work; internal workers recheck the applicable authority and cancellation revisions rather than impersonating an old interactive session.[^scheduling]

Consent revocation, membership removal and signing are each authoritative domain transitions with audit in the same transaction. Signing checks the expected draft/edit revision, active membership, verified Representative evidence and applicable consent, and freezes the Signed plan. The precise signature contract belongs to [Decide Representative verification and signature evidence](https://github.com/wescodess/cadet2/issues/37). Revocation cancels future sharing/work without erasing the separately retained Signed plan/audit. An unknown/missing authority record denies access.

Pathway/rule/admin-review writes also commit their audit atomically in C. Remove the current pattern of changing SQL state and appending a governance event in a later request step. A failure to write required audit prevents the corresponding new transition from committing. This is application-controlled append-only history, not a claim of provider-level WORM or protection from a deployment administrator.

### Auth operations and transitional SQL

Use a proved component user trigger for an atomic minimal principal binding where possible; an entire sign-up endpoint can still span several operations. Authentication by itself grants no Practice or Case access. Missing/incomplete bindings remain denied and can be reconciled idempotently; never compensate a timeout by deleting an identity that another operation may already use.

If legacy SQL auth coexists with C during a controlled migration, there is no distributed transaction. Auth registration commits first; reconciliation/bootstrap binds the verified issuer/subject to a pending principal. Keep the old and new environments/authorities isolated through cutover; this transitional contract does not approve an ongoing SQL-backed pilot. A future explicit SQL-auth-only revision would inherit these ordering rules.

For account disable/deletion, commit an application access-denial fence and lifecycle work item in C **before** revoking sessions or deleting credentials, including any transitional SQL copies. Disable the raw auth-delete bypass. Reconciliation retries cleanup and checks its outcome; failures leave the principal denied and cleanup pending. Keep minimal subject mappings/tombstones until all dependent deletion and backup-replay obligations complete. Other auth operations can likewise span multiple adapter transactions; one store or transactional triggers do not turn an entire HTTP flow into a single transaction. The tenancy decision must prove this fail-closed behavior.

### Document bytes and exports

Admit an upload by atomically reserving quota and a pending metadata record in C. Transfer bytes to a private quarantine object with an opaque, immutable key/version through a bounded Canadian path. Bind completion and trusted scan results to that exact version, size and checksum. Only then may a mutation mark the document available after rechecking current sharing authority. Upload completion, object tags or a delayed scan event alone cannot publish a document. A provider success followed by a metadata failure leaves an inaccessible orphan for idempotent reconciliation/expiry cleanup, not an accessible untracked file.

Deletion first tombstones/denies the document in C and creates a durable cleanup intent. Delete every relevant live/noncurrent version, incomplete upload and derivative; record provider outcomes before marking live-object cleanup complete. A provider error leaves the object inaccessible and deletion pending. Backup expiry/media erasure is a separate status. Restore replays tombstones before serving data.

Use an authenticated Canadian download path that checks current ownership, membership, Case sharing/consent or the applicable retained-record rule, and scan/lifecycle state on each new request, including Range/retries. Do not persist public or long-lived bearer URLs. The available vault research recommends S3 plus a same-region scanner; Convex storage plus a Canadian scanner is also viable. Neither paid arrangement is selected here. Convex's direct `getUrl()` is not a revocable Case grant; the detailed vault/limits choice remains in [Define solo Client utilities and reminder behavior](https://github.com/wescodess/cadet2/issues/41), informed by [Research Canadian document vault storage constraints](https://github.com/wescodess/cadet2/issues/40).[^vault]

Export generation follows the same pending-artifact pattern. Recheck current requester authority and relevant revisions before publication/download; a queued export cannot preserve access lost while it ran. Export renditions cannot feed mutable profile or plan state back into the authority.

### Reminder/email effects

Commit reminder changes, a uniquely keyed occurrence and an outbox intent in C. A worker claims one bounded attempt, rechecks schedule revision, suppression, consent/preferences and current authority, then calls the approved transport. Cancellation is authoritative even if old scheduled work still wakes up. A provider callback updates only the correlated delivery receipt after authentication and deduplication; it cannot reopen cancelled work or change a Case/plan.

An external send is not atomic with Convex. A timeout/crash after possible provider acceptance becomes `send_unknown`, not an automatic retry that pretends exactly-once delivery. Retries use the same occurrence key where the provider supports deduplication; reconciliation and any duplicate-send policy belong to the utilities decision. Generic notices contain no immigration dates, assessment content, documents or Case labels. Recipient addresses and delivery metadata remain identifying data even with a generic body. Capture is the initial synthetic transport; SES `ca-central-1` is a researched recommendation pending its residency/account/spend gates.[^email]

1. Inventory the selected environment and authorize the migration separately. Generate fresh synthetic fixtures for new pilot environments instead of importing unknown data.
2. Dry-run a versioned, resumable importer in isolation. Preserve legacy IDs through aliases and validate typed payloads, row counts/hashes, all run/snapshot/refresh links, rule order/uniqueness, audit provenance and review links. Quarantine ambiguous ownership, missing snapshots and unverifiable history; do not guess missing evidence.
3. Quiesce writes to each migrating authority, drain/fence old workers and capture a final checkpoint. Import and reconcile before switching readers and writers together. Do not dual-write mutable domain records indefinitely or let an old SQL writer remain live after cutover. Keep the rollback source read-only; reopening it requires reconciliation of any new C writes.
4. Exercise auth, admin, history/compare, refresh, export/deletion and isolated restore. Stop on mismatched references or authority; a seeded/hardcoded catalog fallback must not hide missing migrated records. Snapshot observed rule contents and the evaluator build/version for future runs. The current mutable rules do **not** supply immutable releases, and absent historical rule/source evidence must remain unknown. Do not manufacture past calculation receipts or verification dates. [Define the honest assessment contract and engine adapter boundary](https://github.com/wescodess/cadet2/issues/35) has settled that the legacy engine's named-program coverage is empty: its generic artifacts remain unknown, with missing calculations/evidence unavailable, even after migration or professional signing.[^assessment]
5. Retire SQL domain reads/writes, runtime `CREATE TABLE` paths and request-time seeding. Archive the historical SQL migration files as read-only migration evidence and remove their execution from builds/runtime. Remove `hub.db`, its build-time migrations, generated SQL-auth glue and unused NuxtHub/PGlite/Drizzle dependencies only after the last SQL consumer, including auth, is gone. Any explicitly revised SQL-auth-only design must instead retain narrowly scoped auth SQL and its migrations/driver; leaving these active by accident is not a cutover.
6. After validation and the applicable retention/owner approvals, destroy obsolete live copies and expire recovery copies on their recorded schedule. Remove old URLs/credentials, revoke old keys and decommission paid SQL hosting only after its last required copy/consumer is retired. Preserve a minimal migration/deletion receipt. Do not equate removing a dependency with erasing a database or backup.

The current intake route writes SQL snapshots then Convex runs and deletes the snapshot on a caught error. A committed remote write followed by a lost response can make that compensation unsafe; the new submission transaction replaces it rather than preserving it as distributed atomicity.[^intake] Current public-function containment remains the independent responsibility of [Security: close public Convex functions and the open AI-search endpoint](https://github.com/wescodess/cadet2/issues/28); this decision does not fix or delay it.

## Export, deletion and restoration

Exports resolve a requesting principal and the permitted scope, then read the authoritative current revision or explicitly requested immutable version. Include the Client's profile/intake, permitted Case records, Signed plan evidence, document manifest/bytes, consent history and reminder state as allowed by the rights contract. Practice exports stay within that Practice's retained work. Exclude credentials, tokens, private JWKS, unrelated Clients/Cases and privileged internal notes not authorized for that requester. The exact field policy belongs to the consent/rights and Signed plan export decisions; an export is not a raw database dump.

Deletion is a durable manifest covering auth, principal bindings, current profile/intake, run/input/edit snapshots, grants/invitations, reminders/outbox/suppression, document metadata and every byte copy, derivatives, exports, caches, logs and backups, plus transitional SQL duplicates. Deny interactive access and invalidate relevant work first; retain only the restricted tombstone/receipt needed for reconciliation and restore replay. Failed steps remain visible as pending/retrying, and retained records are reported with their retention basis rather than counted as erased.

Deleting an account must not cascade blindly into a Practice's retained Signed plans/audit, nor justify retaining every raw upload forever. Keep those records structurally separate, with minimal signer/actor evidence surviving account/membership removal. Consent revocation stops future sharing independently of a full privacy-deletion request. Retention durations, legal holds, dependant authority, and post-revocation access/export rights are left to the consent/rights decision and pending-counsel legal work; this record invents no statutory retention period.

Restore is not complete when a DB snapshot loads. Inventory component tables, domain tables, bytes, any SQL auth, configuration, signing keys and pending-work state; prove component export/import coverage at the chosen versions. Convex backups do not include code, environment variables or scheduled functions, so recreate work from the durable outbox with deduplication and apply deletion/revocation tombstones **before** re-enabling access or dispatch. Keep an independently recoverable copy of the minimal deletion/revocation journal and its completeness watermark in the approved Canadian recovery boundary, outside the snapshot being restored. If post-snapshot journal completeness cannot be established, the restored environment stays disabled. Record recovery-copy expiry separately from live deletion and do not claim provider physical erasure without evidence.[^hosting]

## Preview, staging and first proof seam

[Decide preview and staging topology and feature gates](https://github.com/wescodess/cadet2/issues/45) must use separate Canadian Convex deployments, auth namespaces/issuers/cookies/secrets, object namespaces, callback origins and capture sinks for persistent staging and disposable preview. There is no SQL service to provision for the target; transitional SQL databases/credentials must be isolated from both pilot environments. Preview expiry is not retention or cleanup proof: tear down bytes, exports, auth tokens, scheduled/outbox work and all temporary copies. Restore evidence belongs to persistent staging, not an expiring preview.

Client-data processing includes Nuxt auth/SSR, uploads/downloads, worker/scanner scratch, email callbacks and logs. A global Cloudflare runtime/proxy/cache is not made Canadian by pointing it at a Canadian database. Recommend a small Canadian Node host, with exact host/tier/capacity/cost and Canadian TLS/log/backup path decided by the environment ticket and funded by the owner. Public information infrastructure can remain separate only if no identifying portal data enters it. Missing required residency/configuration denies the feature; there is no silent local-filesystem, non-Canadian, in-memory or alternate-provider fallback.

CI uses generated synthetic people/files and dedicated disposable test state. Do not provide shared staging/production credentials, unknown existing datasets or auth dumps to hosted build jobs. The baseline NuxtHub build can access SQL when a URL is present; remove that path at cutover and keep any transitional migration/build that needs SQL credentials inside its approved boundary. CLI region commands from newer docs are not presumed available in the lock's Convex `1.32.0`. Verify provisioning tooling separately, and inventory regional logs/backups/support, quotas and cost caps even with a regional database.[^hosting]

**First test seam: an authenticated Case-intake submission against the actual isolated Convex backend**, using two Practices, separate Cases and a Client with one granted Case. No admin-key bypass or in-memory fallback may stand in for the evaluator:

- An authorized submission produces one immutable snapshot, one run intent, one audit event and one durable work intent. An injected failure after the snapshot write rolls all four back. Retrying after a simulated lost response returns the same IDs; changed inputs with the same operation key conflict.
- Anonymous callers, forged `userId`, foreign Practice/Case, removed membership, revoked consent and stale intake revisions create none of those records. Test direct public functions as well as Nuxt routes. The other Practice and the Client cannot read unsigned personalized output.
- A rule edit or profile correction cannot change the captured inputs/rules. A revoked Case or fenced old worker cannot finalize new work from an old attempt. Historical imports with a missing SQL snapshot or conflicting owner are quarantined rather than silently accepted.
- Follow with auth-store session-revocation proof, current-grant export/download checks, scan/delete failure reconciliation, ambiguous email acceptance and a restore that cannot resurrect deleted data or resend old occurrences. These extend the same authority and outbox seam.

These are acceptance requirements for [Define pilot acceptance evidence and test-first seams](https://github.com/wescodess/cadet2/issues/50), not tests run in this decision. Record passed, failed, blocked and unrun evidence separately.
