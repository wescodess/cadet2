# Practice tenancy and authorization boundaries

Decision date: 2026-11-17. Status: **answered-on-auto** for the private staging-pilot specification. Baseline: `dev` at `fe2b4a4e4f8b4b861fb5c92661b9e411a84ef0b3`. Resolves [Decide Practice tenancy and authorization boundaries](https://github.com/wescodess/cadet2/issues/34) under [Chart the Client and Representative portals for a staging pilot](https://github.com/wescodess/cadet2/issues/29). This is a decision, not an implemented security fix or pilot approval.

**Use Convex-hosted Better Auth through its official component, application-owned Practice memberships and Case grants, and the same current-authority evaluator for direct Convex calls and Nuxt-mediated calls.** Replace the alpha Nuxt auth wrapper with a thin same-origin Nitro proxy; Nitro never constructs a SQL-backed Better Auth instance. A Client identity is independent of Practice employment. Workforce access requires an active membership, an explicit Case assignment and the applicable per-Case consent. Signing additionally requires a currently verified Representative. Practice administration and cadet2 administration confer neither general Case access nor signing authority.

The architecture and rejected alternative are recorded in [ADR 0003](../adr/0003-case-authority-outside-auth.md). No store decision is reopened, and the organization plugin is not enabled as a parallel membership system.

### Request and token topology

1. Mount the official component with `app.use(betterAuth)` in `convex/convex.config.ts`. `createAuth(ctx)` uses `authComponent.adapter(ctx)`, `betterAuth/minimal`, and `convex({ authConfig, jwt: { definePayload: () => ({}) } })`. Use component `registerRoutes` in `convex/http.ts`: it constructs an auth instance for each HTTP action, which has `runMutation`. Do not cache a query-context auth instance for later HTTP requests.[^component]
2. The Canadian Nitro server proxies only the configured `/api/auth/*` route to that environment's fixed Convex HTTP origin. Preserve method/body, needed cookies, original allowed `Origin`, and every separate `Set-Cookie` header; forward responses without caching or logging credentials. Apply size/rate limits. Reject arbitrary destination URLs, redirects to unapproved origins and caller-supplied forwarded-host overrides. Set Better Auth `baseURL` to the exact configured public Nuxt origin with `basePath: /api/auth`; use exact trusted origins and host-only Secure/HttpOnly/SameSite cookies in hosted environments. If the component's forwarded-origin headers are needed, overwrite them with configured values. No wildcard preview origin, dynamic request-derived issuer or cross-domain plugin.[^proxy]
3. Better Auth owns users, credentials, sessions, verification/reset tokens and signing keys in the component. Enable verified-email password login, verification/reset callbacks through the approved Canadian capture/mail path, and session revocation on password reset. Disable raw account deletion; the data-rights workflow must deny domain access before auth cleanup. Do not enable social linking, anonymous auth, impersonation or optional auth plugins without a new reviewed need. Turn off auth telemetry and credential-bearing debug logs. Provider/account gates remain with the existing environment/email work.
4. The browser uses `createAuthClient` from `better-auth/vue` plus `convexClient()` from the component client plugins against the same-origin proxy. It supplies a fresh token callback to the owned Convex client, honoring force-refresh and clearing auth on failure/logout; bearer tokens stay in memory, not local storage. The HTTP token path remains `/api/auth/convex/token`; at 0.13 the server API key is `getConvexToken`, not the old `getToken`.[^upgrade]
5. Configure Convex with `getAuthConfigProvider()` for this deployment: **issuer = fixed `CONVEX_SITE_URL`, audience/application ID = `convex`, algorithm = RS256, JWKS = that site's `/api/auth/convex/jwks`**. The public Nuxt origin and token issuer are distinct configured values. Token TTL is 900 seconds; payload contains only protocol identity fields plus component-added `sessionId` and `iat`. Do not copy email, roles, membership, licence status, consent, profile facts or Case IDs into JWT authority. No localhost fallback outside the isolated local harness.[^jwt]
6. Nitro protected SSR/API calls obtain a token by forwarding the current request's cookies to the fixed auth endpoint. Use a new `ConvexHttpClient` with `setAuth(token)` per request, then invoke the same guarded user function a browser could call. Never share mutable authenticated clients between SSR requests, serialize bearer tokens into hydration, or instantiate component auth with a fake Nitro context. Validate identity through the guarded Convex principal operation before rendering protected data. Pages may instead defer protected subscriptions until authentication is established; an unauthenticated SSR fetch must not stand in for a protected read.
7. Authenticated SSR payloads and APIs are private/no-store; disable prerendering, shared CDN/query caches and service-worker persistence for private routes. Use explicit response DTOs, not raw auth/component documents. UI middleware provides navigation, while every API/function is independently guarded. Unavailable token minting, component/session lookup or required configuration returns unavailable/denied with no private payload.

### The fix selected for the session-revocation defect

The selected fix for [the logout defect](https://github.com/wescodess/cadet2/issues/53) is **Convex-hosted auth using the official component adapter in a fresh HTTP-action context**, replacing the SQL/Drizzle use of the component plugin. The current and selected plugin sources both suppress writes when the adapter lacks `isRunMutationCtx`; updating the plugin while leaving it on SQL is therefore excluded. The selected adapter sets that marker from `runMutation`, which the component HTTP action supplies. This is source-backed reasoning about the correct topology, not an end-to-end fix already proved.[^component]

New tokens and existing JWTs both require live session admission below. Sign-out must delete the session even after `/get-session`; its session trigger must invalidate the corresponding admission fence. A retained cookie must fail further token minting, and an already-issued JWT must fail protected data reads immediately after committed revocation. Renewal must update the real session and its fence. Password reset, revoke-session, account disable and deletion use the same denial seam. Cookie deletion or a 15-minute JWT expiry alone does not meet this contract. The UI clears local private state on a logout attempt but reports server logout complete only after revocation acknowledgement; a failed/unavailable request remains an error or pending outcome.

Upgrade directly from component 0.10 to the selected supported set following the 0.13 guide and Better Auth 1.5/1.6/1.7 changes. No intermediate deployed version is required. Review endpoint renames, issuer/JWKS rotation and schema/adapter changes. Organization-team backfills are inapplicable to this baseline, which has no such tables. SQL identity/credential mapping, controlled reauthentication, session/token invalidation, isolated dry-run/restore and SQL retirement remain exactly the system-of-record cutover gates. Never reconstruct an existing identity by matching email. If proof fails, block activation and bring concrete failed gates back to the system-of-record decision before considering SQL-auth-only; do not implement an automatic fallback.[^upgrade]

## Principals and the authoritative grant model

The component is the sole authentication authority. Application Convex records reference its trusted subject through the system-of-record decision's stable principal binding `(environment, issuer, subject)`. Email, URL IDs, `activePractice`, role strings, JWT extras and caller `userId` never establish the actor. Missing/ambiguous bindings deny domain access; user creation may create only a minimal binding, not a Practice/admin/Case grant.

The following are record responsibilities for implementation, not a final schema:

| Record | Authority and invariant |
| --- | --- |
| Principal | Stable binding, lifecycle status and access revision. A global disable/delete fence denies all new interactive domain access before credential cleanup; re-enabling does not restore removed grants. |
| Session admission fence | Component-session reference, bound principal/subject, expiry, status and revision; **no session token or credential**. Component session create/update/delete triggers maintain it synchronously with the underlying operation. It is a fail-closed invalidation dependency, never an alternate login/session store: admission still requires the live component session/user. Missing, mismatched or stale fence denies access. |
| Practice / membership | One active membership per `(Practice, principal)`, with work role Staff or Representative, independent `canManagePractice`, status and revision. There are no competing organization-plugin members. Practice suspension denies new workforce work. |
| Invitation | Application-owned purpose, Practice, intended recipient, proposed role/capability or connection, inviter authority revision, expiry, hashed credential and terminal state. An invitation is not membership, consent or licence verification. |
| Case / Case assignment | Immutable Practice and Client binding; separate explicit member assignments with allowed actions, status and revision. An assignment references a membership in that same Practice. Case children resolve that binding; forged cross-Case parent/child combinations deny before reading contents. |
| Consent | Case, Client, permitted recipients/purposes/data/actions, status, revision and any expiry supplied by the consent decision. No global-profile or all-Cases grant is inferred. |
| Representative verification | Principal-bound manual licence check and status/revision, with regulator/link/reviewer evidence. Membership or a verified mailbox cannot create it. The verification decision supplies evidence validity/recheck rules. |
| Platform grant | Principal-bound cadet2-admin capability, status, grantor/operator evidence and revision. No email lookup, first-user rule or reusable bootstrap allowlist. |
| Audit / work intent | Required transition audit is atomic with grants/state. Work records bind the initiator, operation, exact Case/resources/revisions, idempotency key and attempt fence; service identity and initiating human remain distinct. |

A person may belong to several Practices and also be a Client. Permissions are evaluated for the requested resource and audience, never combined into a global maximum role. For a Case where the actor is the Client, enforce the Client projection and deny workforce review/signing of that same Case in this pilot. Employment on other Cases remains independent. A solo Client has no synthetic Practice and receives no Draft assessment endpoint.

Until that policy is available, retained reads/exports deny. **Public** means a deliberately published, Client-free information projection and may be anonymous only on the reviewed public allowlist. A dash denies the action. Admin columns show only their additional powers; a separate lawful workforce role still goes through Case work.

## Practice membership, invitations and switching

Use **application Convex tables** for all Practice workforce membership and invitations. The organization plugin would supply convenient APIs but requires extending the component schema and still cannot enforce Case consent, retained-record rights or signing. Maintaining both ledgers would create a revocation ambiguity. Application ownership accepts the work of invitation security, last-administrator checks and audit in exchange for one transactional domain authority. No Local Install is needed merely to model a Practice.

A membership's work role is Staff or Representative. Representative status pending a manual check can prepare work but cannot sign. `canManagePractice` is a separate capability, not a third professional role. There is no legal “Practice owner” role in the pilot; **Practice administrator** is the canonical term. For the private pilot, Practice creation requires an explicit operator-provisioned `practice.create` grant bound to the designated verified, onboarded principal. Signup alone supplies no such grant. One guarded mutation consumes it and creates the Practice, that principal's active Staff membership, initial administration capability and audit atomically. It does not verify them as a Representative or disclose any Client. Design-partner account selection/provisioning stays with the existing owner-access work; a general self-service Practice signup funnel is not specified here.

Practice administrators may invite/remove/suspend members and change work roles or administration capability within their own Practice. They cannot grant cadet2 admin, licence verification, Client identity or consent. New privileges take effect only through audited mutations with an expected revision. Prevent removal/demotion/suspension of the last active administrator in ordinary Practice operations; transfer administration to another active member atomically first. Global security suspension may freeze the entire Practice even if only one administrator remains. A departing/removed member loses Case and retained-record access in that same authority transition; do not restore their assignments automatically on rejoining.

Case assignments require an active same-Practice membership and an explicit Case-management grant held by an already authorized Representative, plus any recipient/scope consent required by the consent decision. Administration capability alone cannot activate an assignment, including self-assignment. The Client's initial Case connection can establish the first named assignment atomically. A Practice administrator can propose a replacement after departure; activation needs the Client connection/consent path or the later explicit retained-record reassignment policy. Until then it denies, rather than silently expanding access. Removing a member does not transfer the Client's Case to that member's other Practice.

Both workforce invitations and Case connection invitations use these mechanics:

1. Store a distinct purpose, exact Practice, intended verified recipient, proposed scope/role, inviter and current authority revision. Generate at least 256 bits of random bearer material, store only its hash, expire after **48 hours**, and support cancellation. No profile, document or immigration facts belong in the invitation/email. Resending rotates the credential and cancels the old one. Rate-limit creation/acceptance; suppress token logging/referrers and remove credentials from the browser URL after exchange.
2. Acceptance requires an admitted, verified-email session matching the recipient under the auth system's email normalization; never apply guessed mailbox aliases or create a new subject by email. Wrong account returns denial without consuming the invitation, logging out the person or silently changing accounts. Unverified recipients must verify first. Invalid/expired/cancelled credentials reveal no Client record.
3. In one mutation recheck purpose, recipient, expiry, pending state, Practice status, inviter membership/admin or connection authority and its stored revision, requested role/capability, duplicate membership and any consent prerequisite. Accept and create the one binding/membership plus audit atomically. Concurrent accept/cancel/change-role races serialize to one valid outcome. Removing/suspending/demoting an inviter invalidates outstanding authority-dependent invitations; accepting an old token cannot recreate that grant.
4. Consumption is single use. The same principal/operation-key retry after a lost response may return the already committed result; any other replay fails and creates no second grant. An existing active membership remains unique; an invitation cannot silently upgrade its role. A removed membership requires an explicit new grant and never revives old Case assignments.
5. Commit delivery intent with the invitation, then use the Canadian outbox/capture path. A duplicate or delayed email cannot change invitation state. Delivery does not create membership or consent. Auth verification/reset links remain Better Auth tokens, not workforce/Case invitation credentials.

An authenticated member may select among only their active Practices. `activePracticeId` is per-tab navigation state, not a session-wide privilege; every request has an explicit target and rechecks the stored membership and child-resource binding. On Practice/account switch, cancel prior subscriptions/requests, clear private caches/rendered data and create new scope-bound subscriptions. Discard late responses tagged with the old principal/scope epoch. A user with different roles in two Practices never carries one role across the switch. A removed Practice vanishes from the switcher and all direct calls deny even if a tab keeps its old ID.

## Client connection and the consent enforcement seam

A **Client connection is not Practice membership**. A verified Client can accept a Practice's invitation, or request a connection using a known Practice/Representative invitation path. This supplies no public directory, marketplace or lead-selling feature. Before acceptance, store a connection proposal with recipient binding; do not fabricate a Client identity or create a Case with an email in place of its immutable Client principal. Staff may prepare a proposal for their Practice, but cannot accept it or grant consent for the Client.

The accepting Client is always derived from the session. A Case is created/bound to exactly that Client and the invitation's Practice, with its first permitted assignment and explicit consent reference in one mutation when the consent prerequisites pass. An acceptance that lacks consent may record a pending proposal, but cannot activate Case data sharing. Per-Case details, 18+/dependants authority attestations, disclosure language and consent-purpose choices belong to [Decide per-Case consent, retention and data rights](https://github.com/wescodess/cadet2/issues/36). Until those required policy fields are defined and satisfied, protected sharing denies.

For an active Case, one evaluator checks `(principal, resource, action, audience)` against stored Case → Practice/Client and the appropriate authority branch. **Client-own** actions require that Case's Client binding and the Client field/action allowlist; the Client needs no workforce membership to supply their own intake or revoke consent. **Workforce** actions require active same-Practice membership, Case assignment, lifecycle and **the current consent for the requested data/action**. **Retained-record** actions use their separate explicit grant/rights policy rather than active sharing consent. **Platform** actions require their narrow admin grant and never fall through into Case access. An endpoint cannot relabel a Client response as workforce output to reveal a Draft.

Profile sharing pins explicitly supplied revisions/fields; a Case assignment does not expose the Client's latest global profile or every vault item. Staff enter Case facts or correction proposals with authorship; they do not overwrite the Client's global profile. A Client with two Cases, even at the same Practice, has separate snapshots, assignments, work, sharing and consent. A guessable valid ID or shared Client identity cannot bridge them.

Consent revocation writes denial/revision and audit atomically and fences pending work immediately. It stops new sharing, assessment/edit/signing, exports and document access under that consent; it does not erase already-delivered bytes or the separately retained Signed plan/audit. A changed grant is a new revision, never restoration by replay of an old consent ID. Re-consent cannot automatically reactivate old jobs or assignments. Practice-retained and Client-rights projections use explicit separate policy/actions; there is no blanket “consent off means everything deleted” or “retention means the entire profile stays open.” Retention periods, holds, exact post-revocation fields, Client access/export/deletion outcomes and dependant authority remain with the consent/rights decision.

Signing is an interactive mutation. Recheck the admitted session, active assigned Representative membership, current licence verification, Case/consent, draft/edit/input/evidence revisions and content digest in that mutation; persist signature evidence, immutable Signed plan, audit and publication intent atomically. A removed member, suspended verification or revoked consent cannot win a concurrent signing race after the denial commits. Staff, unverified Representatives, administrators and workers cannot sign. Signature evidence/recheck policy remains with [Decide Representative verification and signature evidence](https://github.com/wescodess/cadet2/issues/37); workflow transitions remain with [Define the Case lifecycle and audit transitions](https://github.com/wescodess/cadet2/issues/38).

## Every backend boundary establishes authority

### Public Convex functions

Every public query/mutation/action has argument validators and an explicit classification. The default classification is protected. A reviewed allowlist may contain auth HTTP routes, public Client-free information/health projections and a minimal identity-state query returning signed-out/denied state. It contains no run, Case, private admin, audit or test function. Static guard coverage is necessary but must be proven against actual behavior.

Protected queries/mutations follow this order:

1. Read `ctx.auth.getUserIdentity()`; reject missing identity, unknown issuer/subject, missing session ID or an identity outside the configured environment. Token validation establishes provenance, not role or current session validity.
2. Use `authComponent.safeGetAuthUser`/the component adapter to read the **live** user and unexpired session. Explicitly bind that session's `userId` to `identity.subject` and the principal. The helper's session existence check alone is not the whole application admission contract. Check verified email, principal status and the matching session fence/revision. No cached session, caller principal, email-based fallback or `tokenIdentifier` fallback substitutes for this binding.[^session]
3. Load only the minimal ownership/scope records needed to authorize the target. Resolve Practice/Client/Case from stored relationships and verify all supplied IDs against them, including run→snapshot→Case, document version→sharing→Case and export→source revision. Apply the matrix action/audience; unknown grants deny. Do this **before reading/adapting the protected payload**, including assessment artifacts.
4. Perform the authorized bounded indexed read or transactional transition. A write rechecks expected revisions and commits required audit/work intent with state. Queries authorize each returned row and field; paginated totals/search/filter facets must not leak foreign/unsigned records. Never load a global table into Nitro and filter it there.
5. Serialize a purpose-specific allowlisted DTO. A Client response is built from Client-owned utilities/intake or immutable Signed plans, never by fetching a Draft and hiding it in the UI. Attach the source/scope revision and validity bounds needed for cache rejection. A denied/missing foreign resource uses a non-enumerating response; operational unavailability remains distinct from a successful empty list.

A protected action authenticates at entry but must call a guarded query/mutation for each data read/write: actions are not transactions and cannot carry a stale authorization result across awaited work. Scheduled functions do not inherit user auth. An action's result publication, download admission or finalization must recheck current authority and resource/attempt revisions; a successful earlier check is not a capability to keep operating after revocation.

### Nuxt routes and middleware

Classify **every** `server/api` route, server-rendered private page and server action as public information/auth, user-scoped, cadet2-admin-scoped or authenticated service callback. No unclassified route ships. Workspace/intake/run/history/comparison/refresh routes use the admitted principal and the matrix's Case or own-Client authorizer. Admin routes call the same backend platform-grant check before provider activity. Client-facing old results/pathways/history/summary URLs are removed or remapped to signed-only projections; an existing user-only route guard cannot authorize them in the new model.

Page middleware uses a minimal server-validated session/permission projection for redirects and state. It never authorizes SQL, a provider or direct Convex functions. Nitro validates arguments, uses the real user's request-scoped JWT client and delegates final authorization to Convex. A `userId`, role, issuer or Practice in headers/body/query is at most an untrusted target, never the actor. Remove request-origin token destinations and `setAdminAuth(... actingAs)` from user flows. Normal Nitro runtime configuration contains no Convex deployment/admin key; deployment tooling retains that credential outside the request process.

The existing AI-search page and endpoint require a current cadet2-admin grant before any provider request, with server-fixed/allowlisted model, system prompt and public-corpus scope. They accept no Client profile/document/Case material. The pilot has no portal LLM path; admin authentication alone is not permission to enable an otherwise disabled provider feature. No rules/RAG source pipeline sends Client content to the non-Canadian public-information infrastructure. Demo tasks and test/seed/reset/mock/delay/fallback routes/functions are absent from all deployed registrations, including preview/staging. A prove-red verify check must detect a reachable reintroduction.

### Internal functions and trusted server calls

Internal visibility is reserved for component triggers, worker claims/finalization, reconciliation, scan/delivery receipts, migrations and operator-only grant administration. Internal means not client-callable; it does not establish the authority of a resource named in an argument. No public generic wrapper invokes an internal function chosen by caller name or accepts an actor/asserted role envelope.

| Path | Required trusted-call contract |
| --- | --- |
| Browser or Nitro acting for a person | User JWT → guarded public function. `ctx.auth` resolves the initiator. Nitro has no deploy-key/acting-as shortcut. Server-only provider work is mediated by an authorized operation, not by giving Nitro an unrestricted internal client. |
| Convex scheduler/action → internal worker | Pass an opaque stored job/attempt reference. Resolve the initiator, exact operation/resources, original authority revisions, expiry/cancellation and attempt fence **from the committed work intent**. Recheck active principal/Practice/membership/assignment/consent appropriate to that operation before each payload read, external effect and final commit. Unknown/missing/revoked/stale state denies and cancels/quarantines the work. |
| External scanner/mail callback or a necessary Canadian service worker | A narrow HTTP action authenticates the configured service credential or provider signature, checks timestamp/replay and correlates the exact pending operation/document version/attempt. It calls only the dedicated internal operation. No human `userId`/role assertion, arbitrary object key, recipient override, generic internal invocation or admin key crosses this boundary. A verified receipt cannot create consent, a signature or a new Case grant. |
| Operator migration / initial or subsequent platform grant | A separately authorized one-off deployment operation calls a dedicated internal function with exact principal, reason and operator evidence; writes mandatory audit. It is not reachable through the normal Nuxt process or a public bootstrap route. |

For a user-created durable job, the initiating actor is the admitted principal recorded at creation; the worker is separately recorded as executor. Logging out does not delete an already-authorized reminder schedule, but a revoked consent/member/principal or changed schedule/attempt fence prevents work that depends on it. A worker may continue only the committed business operation, never mint a new user identity or sign. Any permitted retained-record or deletion job uses its specific retained/rights scope instead of pretending the old live consent remains active. The system-of-record transaction/outbox, ambiguous-provider-result and restoration rules continue to apply.

The immediate containment ticket may make legacy Nitro-only functions internal as an intermediate measure; that does not certify its existing admin-key caller for the pilot. The pilot contract removes that bypass for interactive work and rechecks scope on all remaining internal operations. No implementation of this decision is performed here.

## Revocation, subscriptions and cached data

Every private live query must read the principal, session admission fence and its relevant membership/Case assignment/consent/platform grant/verification records **as reactive dependencies**, including lists, counts, history and download/export readiness. Do not check authority only while establishing a WebSocket or in a one-off HTTP preflight. A session create/update/delete trigger updates the application fence in the same underlying component operation; throwing on an unmaintainable fence prevents that operation from committing. Domain revocations change their grants and audit in the same mutation. One Better Auth HTTP endpoint can still contain several database operations: a trigger does not make the entire endpoint transactional.[^triggers]

Upon committed logout, removal, suspension or consent revocation, dependent subscriptions re-evaluate to denied/redacted state and cease disclosing that scope even with an unexpired retained JWT. A change to one Case leaves other independently granted Cases intact. Current licence loss prevents new signing; it does not rewrite historical signature evidence. Any reduced preparation/read entitlement must likewise be reflected by its relevant grant. Account disable first sets the principal denial fence, then revokes auth sessions through retryable cleanup; failed cleanup cannot reopen domain access.

Time passing alone is **not** a Convex data dependency. When a session or timed consent/grant changes, schedule an internal expiry mutation with its expected revision to invalidate the fence at expiry. Renewals supersede old expiry tasks; old tasks cannot expire a renewed session. Every backend evaluation also compares stored expiry to the server clock. DTOs carry a `validUntil` no later than their earliest applicable expiry; the client clears private state at that bound and while disconnected/reconnecting, then revalidates before rendering. Never rely only on a `Date.now()` comparison in a query to make an otherwise idle subscription disappear. Timer/expiry/invalidation behavior must be proved on the actual backend; scheduler failure is not permission to serve an expired grant.

On denial/auth error, clear rendered private content and caches, cancel requests/subscriptions and require fresh admission. Ignore older in-flight responses using the principal/Practice/Case epoch and source authority revisions. On reconnect/reload/history navigation, reauthorize before showing persisted SSR/query state. No durable offline private replica, shared private cache or long-lived public/bearer download URL is part of the pilot. Every new download, Range/retry, export publication and export download checks current scope and document/version/scan status through the approved Canadian path.

Revocation prevents subsequent admissions/disclosures and clears a cooperating portal's view; it cannot erase a payload admitted before the revocation commit, a screenshot or an already-downloaded file. Concurrent operations serialize at the authority mutation/read boundary: a request admitted before the commit may already be in flight. Tests must verify the actual subscription invalidation and absence of **new** protected updates after revocation, without claiming recall of previously delivered bytes.

## cadet2 administration and its limits

Use one application-owned platform-grant authority keyed to the stable principal. Migrate any valid `rag_admins` grants through an explicit subject-binding review; remove email-based fallback, request-time allowlist bootstrap and the public admin-sync route as grant mechanisms. A verified email or matching environment-variable string is not an admin grant.

The owner-controlled deployment operator grants/revokes cadet2-admin capability using the dedicated audited internal operation. The initial target principal must be supplied/confirmed through [Owner: provide Canadian staging accounts and access facts](https://github.com/wescodess/cadet2/issues/46); no account is invented here. Later grants use the same operator path; the pilot has no self-service admin promotion or UI for granting more platform admins. Grant/revoke requires exact principal/environment, reason, operator evidence and expected revision; lookup/audit failure denies. Deployment credentials do not live in Nuxt or a browser.

cadet2 admins may perform the minimum licence-check workflow, govern pathway/rules/public sources, view permitted operational diagnostics and apply audited security suspension. They cannot read arbitrary Client profiles, vaults, Drafts or full Case audits; create/restore consent; add themselves to a Case; impersonate/reset a user's identity to act as them; sign/release/correct a Signed plan; forge audit actors; or waive region, scan, evidence, consent or verification checks. No generic “superuser” branch exists in the Case evaluator.

Licence verification records name, licence/regulator reference, checked link/time, reviewing admin and current status; the verification decision owns exact evidence, expiry and recheck rules. An admin cannot approve their own licence. An admin who is also a Representative must independently hold active membership, assignment, consent and a verification checked by another authorized admin to sign a permitted Case. A platform-grant revocation removes admin functions/subscriptions without automatically revoking independent Client/workforce rights; principal suspension removes all interactive rights. Administrative review of a run remains governance, not professional signature or engine evidence.

## First test seams and evidence requirements

Start test-first at the **actual session + Case authority boundary**, before replacing page routes. Use generated synthetic identities, two Practices, two Cases for one Client (including same-Practice Cases), a foreign Client, Staff, pending and verified Representatives, an administrator-only member and a cadet2 admin. Exercise the real isolated Convex backend/auth component and Nitro with the same principal; a mocked `ctx.auth`, in-memory grants or deployment-key client is not proof of JWT/session or tenancy isolation. These are proposed acceptance tests, not tests run here.

| Seam | Required deliberate-red/positive evidence |
| --- | --- |
| Anonymous / malformed identity | Direct public functions and Nitro deny missing/invalid/expired/wrong-issuer/wrong-audience tokens before payload reads or writes. Forged `userId`/role/headers do nothing. A valid admitted user remains the positive control. |
| Auth topology / logout defect | Reproduce the baseline `/get-session` → `/sign-out` failure first. On the selected topology, session renewal persists; logout deletes the server session and fence; a retained cookie cannot mint (401); an existing JWT cannot read; a second tab's subscription is denied. Include reset/revoke/disable and a real proxy/SSR/browser round trip, not just isolated package tests. |
| Cross-Practice | A member of A cannot read/write B's Case, run, snapshot, documents, audit, count/search/history or export, even by pairing B's child ID with A's Practice ID. Multi-Practice user roles remain separate; Practice/account switching discards late old responses. |
| Cross-Case | One Client with Cases C1/C2 grants only C1: no C2 profile revision, intake, Draft, document, reminders or exports through C1. Repeat for two Cases at one Practice, a mismatched run/snapshot, and a Client who also has a workforce role attempting to review/sign their own Case. Client-owned global utilities are not exposed by a Case assignment. |
| Signed-only Client projection / signing | All Client results/history/comparison/SSR/export/deep links exclude Drafts and Staff notes. Staff, pending Representatives and admin-only roles cannot sign, including forged signer IDs or worker calls. A current assigned verified Representative can sign the exact revision once; changed revision/evidence/verification or concurrent revocation denies. |
| Consent revocation | Revoke while a Draft, export, download or worker is pending: subsequent reads/effects/publication deny; no new file URL or Case update arrives. A separate consented Case still works. A retained-record projection, when specified, contains only its separately allowed signed/audit fields. |
| Removed/suspended member | Removal/suspension immediately denies direct/Nitro/live and retained-record workforce access with the same still-valid JWT. Demotion immediately denies lost actions, especially signing/Case management, while separately permitted Staff preparation is a positive control. Rejoining does not restore old assignments; an old invitation cannot revive removed privileges. Last-administrator ordinary transitions fail atomically. |
| Live subscription / expiry | Keep the WebSocket and JWT alive during logout, principal/Practice/member/consent/admin-grant changes; observe denied/redacted results and no later protected updates. Prove session-trigger fence atomicity by fault injection. Test idle session/consent expiry, scheduler delay, renewal racing old expiry tasks, disconnection/reconnect and stale SSR/cache rejection. |
| Invitations / connections | Wrong account, unverified email, expiry, cancellation, role/inviter changes, sequential/concurrent replay and lost responses create at most one valid grant. Case connection never adds workforce membership or shares data before explicit consent. |
| Internal/service authority | A normal client cannot invoke internals; a valid service with a foreign/stale job/document version/attempt cannot finalize it. Forged actor/service headers, wrong environment, expired/replayed callbacks and public generic wrappers deny without provider effects. Logout does not fabricate worker identity; revocation cancels its dependent work. |
| Admin / bootstrap | Email-only allowlist, first signup and missing/failed grant lookup cannot bootstrap or create a Practice. A Practice administrator cannot activate self-assignment by that capability alone. A cadet2 admin can perform the scoped verification action, cannot verify self or read/sign an unrelated Case, and loses admin subscription access when the grant is removed. |
| Coverage and provenance | Inventory all exported Convex functions and Nuxt routes against the classifications. Prove a guard removed or a test/mock/seed/reset/fallback route reintroduced makes verify fail; prove an identity-only guard still fails cross-Case tests. Preserve assessment standard-creation/per-artifact provenance and one processing claim; old unverified runs remain unavailable. |

Use positive controls alongside each denial, and record the failing pre-fix run and passing post-fix run against the real source-of-truth evaluator. Atomic intake/snapshot/run/audit/work, idempotency and restoration tests from the system-of-record decision remain required. A passing unit suite alone cannot establish live invalidation, provider residency, credential migration or staging readiness.
