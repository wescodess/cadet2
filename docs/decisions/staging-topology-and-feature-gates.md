# Preview and staging topology and feature gates

Decision date and provider observations: **2026-11-17**. Resolution: **answered-on-auto** for [Decide preview and staging topology and feature gates](https://github.com/wescodess/cadet2/issues/45). Account, spending, immutable-region creation, keys and DNS actions remain open in [Owner: provide Canadian staging accounts and access facts](https://github.com/wescodess/cadet2/issues/46). Nothing was provisioned, deployed or purchased. [ADR 0006](../adr/0006-isolate-preview-and-staging-authority.md) records the isolation decision.

## Decision

**Use an isolated Canadian Node/Nitro application plus Canadian Convex for staging; give every PR a disposable local stack built from its exact head, with the real backend and auth, never stubs or staging's backend.** Convex owns auth and portal data; private document bytes and scanning have a separately verified Canadian boundary. Start with captured email. Server-owned Convex flags default off, and self-serve planning stays off.

The provider recommendation, subject to the owner's account/budget and engineering's boundary checks, is **reuse suitable verified Canadian capacity first; otherwise Google Cloud Run in Montréal, request-based billing, minimum zero instances, plus Convex Free Canada Central and conditional S3/GuardDuty Canada Central**. The illustrative small-pilot total is **US$0–5/month**, including a bounded allowance for artifacts, secrets, regional logs, bytes, scans, events and recovery. This is an estimate under the explicit workload below, not an approved purchase, a guaranteed free deployment or a billing ceiling. If the owner funds nothing or required placement cannot be proved, hosted staging remains blocked while Canadian local preview work proceeds.

This settles the architecture and fallback preview method. It does not settle an account's capabilities or authorize activation. No production project, region, DNS name, live recipient service or paid plan is selected here. Staging should use a platform that can later be mirrored with separate production services, but a future production arrangement needs its own decision and authorization.

### Exact auth and domain arrangement

One staging app origin serves both portals and `/api/auth/*`; paths do not require separate subdomains or wildcard cookies. Set Better Auth's base URL to that exact app origin and its path to `/api/auth`. Nitro proxies to the fixed environment Convex HTTP site, preserves separate `Set-Cookie` headers and overwrites forwarding headers from trusted configuration. Reject arbitrary upstream URLs, request-derived host/issuer values, unapproved redirects and wildcard origins.

The token issuer remains the **Convex site origin**, JWKS is `<CONVEX_SITE_URL>/api/auth/convex/jwks`, audience is `convex`; the app origin is distinct. Use host-only Secure/HttpOnly/SameSite cookies on staging. Verification, reset and invitation return URLs are exact same-origin allowlisted paths; verify/reset tokens never enter generic logs/capture lists. No social OAuth provider/account is needed. Local preview uses explicit loopback origins/ports with its own issuer; insecure local cookies are allowed only there. Cross-environment tokens/cookies must fail direct Convex and Nitro calls.

For the Cloud Run recommendation, use the service's HTTPS **`run.app` origin initially**. It needs no domain purchase or DNS edits. Direct Cloud Run domain mapping does not list Montréal/Toronto among its supported regions; a vanity staging domain requires another ingress arrangement and a new cost/residency check. Do not CNAME a custom name and assume TLS works, use Firebase/global CDN as an unreviewed shortcut, or route through a foreign service to make a URL prettier.[^domain]

## Byte storage, scanner and email

Recommended conditional hosted vault: **S3 Standard plus independent GuardDuty Malware Protection for S3, all `ca-central-1`**, with regional EventBridge events and a narrowly privileged regional relay to the guarded Convex completion operation. Independent malware protection does not require purchasing unrelated GuardDuty protection plans. Budget the relay, S3 operations/tags, logs, transfer and recovery separately. Credentials cannot mark their own uploads clean; authenticate provider events, correlate immutable version/checksum/attempt and deduplicate/reconcile missing events. Provider events that are late, failed, unsupported, mismatched or absent never publish bytes.[^scan]

S3 regional list prices: **$0.025/GB-month**, PUT/COPY/POST/LIST **$0.0055/1,000**, GET/other Tier 2 **$0.00044/1,000**. GuardDuty includes 1 GB and 1,000 monitored PUTs/month; above those, **$0.1035/GB + $0.246/1,000 objects** in Canada Central. Regional public price lists were re-read; do not use a US example as the Canadian quote.[^aws-storage-price]

Use private staging-only quarantine/version keys, public access blocked, TLS, provider-managed encryption initially, no replication outside Canada, and explicit finite object/log/backup retention. Downloads stream through a guarded Canadian app/backend path, rechecking owner/Case/Consent/scan/version on each new or Range request; expose no provider bearer download URL. Enforce PDF/JPEG/PNG, 1 byte–10 MiB, 25 versions/250 MiB per Client, two concurrent reservations, actual streamed size/type/checksum and parser safety from the utilities contract. A clean malware result does not replace technical file validation or professional evidence review.

Canadian Convex file storage plus a verified Canadian ClamAV/runtime is an alternative; its scanner memory, signature freshness, execution, recovery and total price are unverified. For local previews use an actual local private object service and ClamAV, pinned images/signature database, with provider-specific S3/GuardDuty behavior proved separately on staging. Do not substitute an in-memory object map, a scanner stub or an environment variable saying “clean”. If hosted storage/scanning is unapproved or unavailable, deny byte admission/download as appropriate; checklist metadata can still work. This partial state is **not vault readiness or full pilot acceptance**. No hosted local-filesystem/R2 fallback.

**Capture is the initial email transport**, persisted in the environment's Convex deployment. Use the real outbox, due work, suppression, rolling limits and idempotency. Enforce an exact server-owned synthetic recipient allowlist across signup, address changes, invites, reset and reminders, with no CC/BCC/override route. The result is `captured_synthetic`, “not sent”, terminal and never flushed to a live provider. Capture failure denies delivery. Auth/invite token receipts are separate, short-lived, narrowly authorized and unavailable from generic Client/operator inbox lists; retrieve them only through approved operator tooling, without a public test endpoint. Staging capture has no SES/SMTP credentials.

Keep `live_email` off. Conditional first live candidate is SES **`ca-central-1`**, only after its abuse/content/metadata/backup/support scope, retention, sender DNS, event authentication, controlled recipients and complete quote pass. The current default for new/inactive regional accounts is Essentials **$0.16/1,000** at the first band; à la carte **$0.10/1,000** is available. Do not assume that plan or time-limited credits. No dedicated IP, Mail Manager, tracking, virtual deliverability or other add-on is justified. Event/log/transfer and $0.12/GB message data can add cost. Sandbox restrictions and simulator calls still need setup and can bill.[^ses]

Use fixed generic utility notices; provider acceptance, delivery-to-mail-server, failure and `send_unknown` remain distinct. Retry known non-acceptance within the utilities contract; never resend unknown/captured/cancelled occurrences after activation, restore or rollback. Staging does not send live auth/invitation mail just because reminder mail is captured. Proving a live mailbox later is separate from capture and is not required to choose this topology.

## Server-owned feature flags

Implement a typed `featureFlags` Convex table keyed uniquely by `(environmentId, key)`. Each row contains `enabled` (default false), `rolloutBps` (default 0, range 0–10,000), exact eligible-principal cohort references, monotonic revision, policy/evidence revision, changer and audit timestamps. Missing/invalid/duplicate rows, wrong environment, unavailable reads or unknown keys evaluate **off**. The trusted deployment configuration owns `environmentId`, synthetic-only mode and provider admission evidence; callers cannot set them. A flag never grants membership, Consent, verification, signature, age attestation or data ownership.

There are **no enableable flags** for legacy Client results, demo/test/seed/reset/fallback routes, YouTube ingestion, arbitrary LLM calls, broad admin Case access or real-data mode. Those remain build/registration or hard-policy denials. A rollback may not add them.

Only an explicitly granted operator `flags.manage` capability can mutate flags, with expected revision, reason/evidence and audit in the same transaction; a browser never writes the table. Return only effective booleans for the current principal, not cohort membership or provider secrets. Enforce one evaluator at every Nitro SSR/API/direct Convex/query/mutation/action and worker boundary. Reactive queries depend on flag revisions; privileged actions and finalization re-read current state, without a stale “last known on” cache. Off transitions fence pending intents; already admitted external effects cannot be recalled. Paused portals retain dedicated, ordinarily authorized withdrawal, cancellation and rights/deletion operations; safety/cleanup does not depend on an enabling feature row.

Percentage assignment uses a stable server hash of environment, key and admitted principal, with a server-owned salt; the client cannot choose a bucket. A cohort percentage is an additional restriction on authorization, never an authorization oracle. For the small synthetic pilot use explicit named cohorts first, then at most 10% → 50% → 100% of that fixed eligible cohort. Bake for a complete smoke and at least 30 minutes at each step; never enable all rows automatically on deploy. Any isolation/signing/privacy failure immediately returns the affected flag to off. Self-serve planner, live mail and AI Search do not participate in this initial ramp.

## Per-PR disposable preview and synthetic seeds

The adopt WEB-TS recipe's fallback is mandatory here: **one exact PR head, one disposable local stack, real backend, no stubs**. The preview harness must:

1. Record PR/head SHA, lockfile digest, QA-tree SHA, container/backend/scanner digests, region/host evidence and a unique preview ID. Use frozen install, Node 24/pnpm 9.12.3 after the quality adoption lands. Select and pin the actual local Convex backend release compatible with the target component/CLI; do not assume the old 1.32.0 CLI supports newer commands.
2. Launch genuine Nitro, Convex backend/HTTP endpoints/auth component, private object service and scanner/capture persistence on isolated loopback/container networks and volumes. An old head also gets its actual required isolated SQL schema. Generate only disposable local secrets. Never configure a staging URL, cloud deployment key or host Docker socket in an untrusted PR container.
3. Build from that PR head, bind explicit ports/origins and wait for readiness including a real backend transaction, auth/JWKS and scanner health. An HTTP 200 from Nuxt alone is insufficient. A local backend that cannot start makes the preview **blocked/failed**; do not swap in `convex-test`, fake sessions, in-process Maps or remote staging.
4. Load versioned fixtures through trusted tooling **outside the deployed application graph** and normal guarded workflows. Run QA-owned journeys from `qa/<ticket-slug>` when available, otherwise integration's QA tree. Keep QA's fixtures/assertions intact; bind them to the PR app/backend under test. The delivered harness must publish its launch command, loopback URL, SHA manifest and sanitized evidence as the per-PR preview.
5. On completion/PR close, stop processes, revoke ephemeral credentials, remove volumes/bytes/capture records and release ports; an exit trap plus a bounded orphan sweep must prove cleanup after failures. Initially serialize full stacks on small reused capacity, with a two-hour idle lease. Distinct previews never share database/byte state, even if the host is shared. No public tunnel or hosted branch frontend pointing at the shared staging backend.

No Canadian runner/workstation has been verified in this decision. GitHub-hosted runner labels do not prove Canada. Existing hosted CI may perform secretless source/static checks, but client-shaped fixture/auth environments and their traces run only on verified Canadian capacity. If that capacity is absent, report the real-backend preview/journey gate blocked and do not relabel a static build as a preview. A future self-hosted PR runner needs isolated disposable execution with no staging credentials; persistent trusted deploy jobs must be separate from PR execution.

## Smoke, monitors and rollback contract

Smoke must cover readiness/version/digest, real login and verification/logout after `get-session`, direct and Nitro cross-Practice denial, current Case Consent withdrawal, Staff cannot sign, Client gets only a real Signed plan, a solo date creating one captured occurrence, and a tiny upload → actual clean scan → authorized download → revocation/deletion. Check anon/foreign file Range, no raw legacy routes/testing registrations and no provider effect while gates are off. Use QA-owned assertions, positive controls, no retries for sign-off and sanitized Canadian evidence.

Run a Canadian synthetic monitor **every five minutes during the declared pilot window**, and an expanded smoke after each deployment/flag ramp. Outside an active pilot window, use hourly readiness and declare that schedule explicitly; a paused pilot makes no 24/7 availability claim. Include login/critical portal reads, one nonbillable/captured idempotent reminder and authorization denial. Run scan/upload smoke after deploy and daily while active within its byte budget, with deterministic cleanup. Monitor from approved Canadian CI/runner capacity; do not buy a global observability service. Notices go through the orchestrator/T3 notification path, not a new Slack/Telegram integration.

Collect platform 5xx/error rate, latency, cold starts/OOM, Convex function failures/quota, oldest due reminder, unknown sends, scanner/event lag and deletion/journal backlog. Proposed synthetic thresholds: ready endpoint within 60 seconds including a cold start, warmed critical reads p95 under 2 seconds, server errors below 1% over 5 minutes with at least 20 requests; two consecutive critical smoke failures stop a ramp. A cross-Case disclosure, unauthorized signature, invalid scan marked clean, unexpected live send or stale session access triggers immediate denial regardless of sample size. Scan pending over 30 minutes and due-work lag over 5 minutes alert/fence affected work. Low volume makes smoke more informative than a percentage alone. Tune performance thresholds only with retained load evidence; do not waive authorization failures.

The release follow-up must implement and prove these **proposed operator interfaces** before staging activation; they do not exist on the baseline:

```sh
# Each command validates an explicit staging manifest, expected revisions and operator authority.
pnpm ops:flags -- --env staging --disable-all --expected-revision "$FLAGS_REVISION"
pnpm ops:smoke -- --env staging --release "$RELEASE_MANIFEST"
pnpm preview:up -- --pr "$PR_NUMBER" --head "$PR_HEAD_SHA"
pnpm preview:down -- --id "$PREVIEW_ID"
```

Disable-all commits one audited revision/fence for all affected capabilities and pending intents. It never disables safety/denial, Consent withdrawal, deletion/recovery tooling or pending cleanup. If Convex itself is unavailable, the app fails closed; for an ingress incident the operator also denies runtime invocation/places the host into maintenance through the approved provider runbook. In-flight already-admitted effects remain subject to the utilities contract.

For the **conditional Cloud Run** host, the documented provider traffic rollback command is:

```sh
gcloud run services update-traffic "$STAGING_SERVICE" \
  --project "$STAGING_PROJECT" --region northamerica-northeast1 \
  --to-revisions "$LAST_GOOD_REVISION=100"
```

This moves traffic to an existing revision and does not rebuild, restore data or revert Convex. Validate the last-good digest/config and current backend compatibility before routing; keep the failed candidate for diagnosis. Target five minutes to deny affected work and fifteen minutes for compatible app traffic rollback, **unmeasured objectives** requiring a staging drill.[^rollback]

For backend code, use a clean verified checkout of the last-good **release manifest**, with its frozen lock and component/CLI pins, and the already delivered deployment-scoped key. After checking schema/data compatibility and deployment identity, the provider command is `pnpm exec convex deploy --yes`. It redeploys that checkout's functions/schema; it is **not** database time travel. Do not switch to an old unguarded backend, dual auth, old SQL or legacy Client results. If compatibility is uncertain, leave flags off and ship a forward fix instead. Candidate digest deployment and backend CLI behavior must be exercised before acceptance.[^convex-cli]

Before destructive maintenance, `pnpm exec convex export --include-file-storage --path "$CANADIAN_BACKUP_PATH"` is the documented export form, targeting only the selected staging deployment; validate component/auth coverage in the actual pinned release. Encrypt/store that snapshot in the approved Canadian recovery boundary. Managed backups exclude code, environment variables and scheduled functions; release manifests, secret references and durable work/journal records are restored/reconciled separately. Free/Starter permits two managed backups per deployment, retained for seven days; budget their I/O and independent Canadian exports. Automated backups requiring Pro are not justification to upgrade this pilot.[^backup]

A **data restore** is a distinct owner-authorized maintenance operation, not an automatic rollback: restore to an isolated Canadian target with reads/sends disabled; verify source/region/version coverage, replay the independent post-snapshot denial/deletion/hold journal to its complete watermark, reconcile auth/object versions and only allowed durable work, suppress every captured/sent/unknown/cancelled occurrence, then prove no resurrection before reopening. A missing journal or component/byte receipt keeps the target disabled. No blind `import --replace`/SQL down migration against serving staging. Teardown deletes all live object versions/partials, event credentials, preview volumes and resources under a scoped manifest, records outstanding provider backup expiry, and never reports a delete marker as physical erasure.
