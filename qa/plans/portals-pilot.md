## Execution contract, devices and environments

All journey actions use visible role, accessible name, label or text locators, typing, normal pointer/touch/keyboard actions, links, back and refresh. Wait for visible outcome/control/URL, never fixed sleeps. No CSS/XPath/test-ID fallback, force click, script injection, API/database manipulation during a journey or app-service stubs (SP L212; PA L153). Failure to locate an action accessibly is an accessibility bug. Arrange per-run data before the journey through signup/admitted public seams or QA scripts calling them; no deployed test/clock/verification bypass.

Auth/invitation security credentials come from the narrowly authorized capture receipt/operator tooling specified in FG, outside generic notification history. Retrieving a synthetic token is an environment fixture step; its consumption still uses the genuine visible auth/link flow. No public capture inbox/test endpoint is added. If the secure receipt mechanism is unavailable, auth-dependent journeys are blocked, never email-verified by database write.

Each journey uses its own accounts/data namespace; multi-actor steps have distinct authenticated contexts. Staging professional identity/contact is the authorized operational participant, separately protected; Client facts remain fictional. Boundary clocks, corruption, callbacks, race scheduling and direct malicious token/API probes belong to separate contract/release tests. Their observed UI aftermath can be explored; they are not hidden manipulations inside a real-user journey.

## Charters

Each charter is a 20-minute session, extended once only with a recorded reason. Run on staging after batch readiness, or on the exact preview for a single-ticket acceptance session; do not substitute preview sessions for the final staging record. Every charter produces `qa/sessions/<date>-portals-<charter-id>-<persona>.md` with build/environment/timebox, applied heuristics, covered and deliberately omitted states, video/trace/screenshots, bugs and risks. A no-bug session still records coverage. Every bug has a regression journey or ticket. PA L170 and SP L225 are the source for these risk areas; personas implement the QA exploration policy.

High-risk batches get all eight affected personas independently; a single session does not count as all of them. B7 also covers each persona because misleading information and unsafe entry can affect any visitor. Existing shared surfaces remain context rather than an excuse to omit batch-specific work.
